# 부하 시험 — 「편성 시작」 동시 1·5·10명 (2026-10-21)

> 질문: 공개 중인 schedulelab.kr에 10명이 한꺼번에 「편성 시작」을 누르면 서버가 버티는지, 사람들은 무엇을 겪는지.
> 도구: `deploy/loadtest.py`(표준 라이브러리만). 방문자마다 다른 `X-Real-IP`를 붙여 루프백(127.0.0.1:8080)으로 보낸다(서버는 루프백에서 온 `X-Real-IP`만 믿는다). 요청 본문은 `KBO.Preset.buildProject()` + `{timeLimitSec:10, init:'SCRATCH', seed:<요청마다 다름>}`. 시드가 같으면 캐시에서 바로 돌려주므로 실행마다 시드를 바꾼다.

## 2. 사용자가 겪는 것

| 상황 | 지금(고치기 전) | 고친 뒤(이 브랜치) |
| :--- | :--- | :--- |
| 10번째로 누름 | "다른 분의 편성이 끝나길 기다리는 중 · 대기 9번째" → 약 14초마다 1씩 줄어듦 → 약 2분 뒤 진행 막대 시작 → 2분 16초에 결과로 이동 | 같음 |

재현 스크립트(개발 Mac, 고치기 전): A가 돌고 B·C가 대기 → B가 SSE를 닫고 2초 뒤 같은 주소로 다시 냄 → 429, B는 아무도 안 보는데 10초를 다 돌았다. C는 stop 뒤에도 QUEUED, 다시 내면 429. 고친 뒤: C는 stop 즉시 STOPPED, 다시 내면 202. 4번째 D가 탭을 닫으면 22.5초에 줄에서 빠졌다(차례는 33초쯤이었다).

## 3. 꼭 볼 위험 점검

- **Cloudflare 100초 무응답(524)**: 생기지 않았다. 개발 Mac에서 schedulelab.kr로 10번째가 되어 121초 기다리고 134.6초에 끝났다(POST 202, 0.5초). 서버는 SSE 응답 헤더를 바로 보내고, 대기 중에도 앞사람이 끝날 때마다(약 14초마다) 순번 이벤트가 간다. 이벤트가 없으면 주석 줄(`: keep-alive`)도 보낸다. 원래 15초마다였고, 이번에 **5초마다**로 줄였다(탭을 닫은 사람을 빨리 알아채려고. 배포 전이라 시험은 15초 코드). 앞사람이 모두 30초를 골라 순번 이벤트 간격이 약 34초가 돼도 keepalive가 그 사이를 채운다.
- **압축(Caddy `encode zstd gzip`)이 SSE를 모아 두는지**: 모아 두지 않는다. 같은 작업을 `curl --compressed`(응답 `content-encoding: gzip`, 브라우저와 같은 경로)와 압축 없이 동시에 받았다. 순번 9→1 이벤트 9개와 시작 이벤트가 두 쪽에 같은 시각(차이 0.3초 이내)에 왔다. Caddyfile은 그대로 둔다.
- **소개 화면의 긴 대기**(`ui/show/show.js` follow): 대기 중에는 "대기 n번째" 글자만 바뀌고 진행 막대는 0에 멈춰 있다. 지난 시간이나 예상 시간은 없다. 10번째 사람은 2분 넘게 같은 화면을 본다. 아래 5절의 제안 참고.
- **30초 선택지**: `/api/v1/info`의 `queueLength`가 0보다 크면 소개 화면이 꼼꼼하게(30초)를 막는다. 다만 (1) 페이지를 연 때·생각 시간을 바꾼 때·탭으로 돌아온 때에만 다시 묻고(5초에 한 번), (2) 서버는 막지 않는다. 그래서 줄이 빈 순간에 두 사람이 동시에 30초를 낼 수 있고, API로는 줄이 차 있어도 30초를 낼 수 있다. 10명이 모두 30초를 고르면(한 작업 약 34초로 어림) 마지막 사람은 약 5분 기다린다. 서버 쪽 제한은 아래 5절 제안.

## 4. 이번에 고친 것(서버, `src/main/java/.../web/`)

1. **아무도 지켜보지 않는 대기 작업은 뺀다**(`JobManager.sweep`, 5초마다). SSE 연결이 하나도 없고 마지막으로 지켜본 때(작업 생성·SSE 연결·끊김·상태 조회)에서 10초가 지나면 "ABANDONED"로 끝내고 IP 몫을 돌려준다. 서버가 스스로 낸 기본 결과 작업(`unattended`)은 빼지 않는다.
2. **대기 중 중지는 즉시**: `stop`이 대기 작업을 바로 줄에서 빼고 IP 몫을 돌려준다.
3. **같은 주소로 다시 누르면 자리를 이어받는다**: 같은 주소의 대기 작업을 1초 넘게 아무도 보지 않으면 그 작업을 빼고, 새 작업을 맨 뒤가 아니라 그 자리에 넣는다. 지켜보는 중이면 예전처럼 429.
4. **실행 순서 = 대기 줄 순서**: runner가 작업을 지정해 돌리지 않고 줄 맨 앞을 꺼낸다(`runNext`). 그래야 3번의 자리 이어받기가 실제 순서와 맞는다.
5. **끝난 작업을 잊는다**: 끝난 지 10분 지난 작업은 메모리에서 지운다(이전에는 영원히 들고 있었다. 작업 하나에 문제 JSON·결과·트레이스가 들어 있다). 결과는 캐시와 결과 파일에 그대로 남아 `/r/<id>`는 영향이 없다.
6. **keepalive 15초 → 5초**: 탭을 닫은 사람은 서버가 다음 쓰기에 실패할 때 알아챈다. 첫 쓰기는 대개 성공하고 두 번째에 실패하므로 5초 간격이면 약 10초 안에 안다.

테스트: `JobManagerQueueTest` 5개(대기 중 중지, 안 보는 대기 작업 빼기·보는 작업 유지, 서버 작업 유지, 같은 주소 다시 내기 자리 이어받기, 실행 순서). `mvn -q test` 29개 통과.

## 5. 제안(코드 안 바꿈)

- `ui/show/show.js`(다른 세션 담당):
  - 대기 중에 지난 시간과 대략의 예상을 보여 준다. 예: "대기 3번째 · 약 40초 남음". 앞사람 한 명에 (생각 시간 + 4초)로 어림한다. 서버가 `queued` 이벤트에 앞사람들의 생각 시간 합을 넣어 주면 더 정확하다.
  - SSE가 이벤트 없이 끊기면 바로 "다시 눌러 주세요"로 끝내지 말고, 같은 작업 id로 한두 번 다시 연결한다. 서버는 다시 연결하면 지금 상태(대기 순번·마지막 best·done)를 재생하므로 자리를 잃지 않는다. 휴대폰에서 앱을 잠깐 바꿨다 올 때 특히 쓸모 있다.
- 서버: 대기 줄이 차 있으면 30초 요청을 10초로 줄이거나 400으로 돌려보낸다. 지금은 화면에서만 막는다.
- 서버: 대기 줄 상한(예: 20명). 넘으면 503과 "지금 사람이 많아요" 안내. 지금은 줄이 한없이 길어질 수 있다.

## 6. 다시 재는 법

```bash
# 개발 PC: 본문 만들기
node -e "process.stdout.write(JSON.stringify(require('./ui/core/preset-2025.js').Preset.buildProject()))" > /tmp/problem.json
# 서버로 복사한 뒤 서버 안에서(대기 줄이 비었는지 먼저: curl -s 127.0.0.1:8080/api/v1/info)
python3 loadtest.py --base http://127.0.0.1:8080 --clients 10 --time 10 --problem problem.json --out run10.json
```
서버 시험은 실제 방문자를 그만큼 기다리게 하므로 한산한 시간에 한다. 시험마다 결과 파일이 `/var/lib/kbo-scheduler/results`에 생긴다(요청당 `.json` 1개). 재계산할 수 있는 파일이라 지우지 않아도 된다.
