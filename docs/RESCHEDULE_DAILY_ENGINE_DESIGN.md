- 정리한 날: 2026-11-07
- 상태: 설계안. 정할 것 4개를 모두 정했다(§8.1). 코드는 아직 없다.
- 요구 사항: `docs/RESCHEDULE_DAILY_REQUIREMENTS.md`(이하 「요구」). 이 문서는 요구 §12의 결정 15개를 그대로 따른다.

## 1. 계획 단위와 도메인 모델

새 패키지 `org.optaplanner.examples.baseball.reschedule`에 둔다. 1차 편성의 `BaseballSolution`과 섞지 않는다. 점수 단계 수(Soft 6)가 다르고, 해(solution) 클래스마다 단계 수가 정해지기 때문이다.

### 1.1 클래스

| 클래스 | 종류 | 내용 |
| :--- | :--- | :--- |
| `RDay` | problem fact | 기간 안의 날 하나. `index`(0부터), `epochDay`, `monday`. 기간의 모든 날을 만든다. 월요일도 빼지 않는다(요구 §4: 월요일은 허용하고 Soft로 줄인다) |
| `RGame` | `@PlanningEntity` | 경기 하나. `id`(아래 §1.4), `home`, `away`(`Team`), `source`(`CANCELLED` / `REMAINING`), `pinned`, `@PlanningVariable(nullable = true) RDay day` |
| `TeamHistory` | problem fact | 구단별로 기간 앞에서 이어지는 값(§1.2) |
| `RescheduleSettings` | problem fact, 불변 | 마지막 경기일 허용 일수, 연속 경기일 상한, 더블헤더 상한, 기준 순서, 이동 허용 차이(§4.2) |
| `RescheduleSolution` | `@PlanningSolution` | `teamList`, `dayList`(value range), `gameList`(entity), `historyList`, `settings`. `@PlanningScore(bendableHardLevelsSize = 2, bendableSoftLevelsSize = 6)` |

- `Team`은 1차 편성의 것을 그대로 쓴다. `Team.prepareIndices`의 `index`, `stadiumIndex`, `distanceTenthsByTeamIndex`가 이미 있다. 잠실 두 구단은 `stadiumIndex`가 같고 거리가 0이다(`input_2025.json`에서 확인).
- `nullable = true`는 OptaPlanner 9.44의 `@PlanningVariable`에 있다(`optaplanner-core-impl-9.44.0.Final.jar`에서 확인). 비어 있는 경기는 Hard 2단계의 「못 넣은 경기 수」로 센다(§4.1).

### 1.2 기간 앞의 경기: `TeamHistory`

기간 시작 전 경기는 탐색 중에 바뀌지 않는다. 그래서 entity로 두지 않고 구단마다 다음 값으로 접는다.

| 값 | 뜻 | 만드는 법 |
| :--- | :--- | :--- |
| `baseMoves`, `baseDistanceTenths` | 기간 앞의 이동 횟수와 거리(144경기 공정성의 앞부분) | **1차 편성 부분**: 원래 일정 그대로. 기존 `ScoreFormulas.summarizeTeam`으로 135경기 연전 경로를 센다. 올스타 휴식기 0km 규칙도 그대로 따르므로 스튜디오가 이미 보여 주는 숫자와 같다. **이미 치른 재편성 경기**(다시 짤 때): 재편성 규칙(§4.4)으로 이어서 더한다 |
| `startStadium` | 기간 첫 경기의 출발 구장 | 이미 치른 재편성 경기가 있으면 그 마지막 구장. 없으면 **1차 원래 일정**의 마지막 연전 구장 |
| `runAtStart` | 기간 시작 전날까지 쉬지 않고 이어진 경기일 수 | **실제로 치른 경기만** 센다(요구 §4 DH-4). 취소된 날은 쉬는 날이다 |
| `lastPlayedDay` | 기간 앞의 마지막 실제 경기일 | 기간 안에 경기가 없는 구단의 마지막 경기일로 쓴다(§4.3) |
| `doubleHeadersUsed` | 이미 치른 재편성 더블헤더 수 | DH-5 상한은 시즌 전체로 센다 |

**1차 편성의 취소 경기는 두 가지로 센다.** 이동은 원래 일정대로 센다. 그 구장에 갔다고 보기 때문이다(결정 10). 연속 경기일은 실제 경기만 센다. 그래서 취소된 날은 이동 계산에서는 「경기한 날」이고, 연속 경기일에서는 「쉬는 날」이다. 이 차이를 코드 주석과 테스트(§6.2)에 남긴다.

기간 앞의 경기에 취소 표시가 없으면 치른 것으로 본다. 1차 편성 기간이 끝난 뒤에만 짜기 때문이다(요구 §3).

### 1.3 기간 안의 고정 경기

- **다시 짤 때 발표한 재편성 경기**(요구 §8)는 기간 안에 있으면 `pinned = true`인 `RGame`으로 넣는다. 날짜는 바꾸지 않는다. 그래도 구단·구장 점유, 연속 경기일, 이동 경로, 점수에는 모두 들어간다.
- 발표한 경기에 새 경기를 붙여 더블헤더를 만들지 않는다. 요구 §8은 「빈 날에 끼워 넣는다」이고, 더블헤더를 붙이면 발표한 날의 경기 수가 바뀐다.
- 고정 경기끼리 이미 꼭 지키는 규칙을 어기면 실행하지 않는다. 예를 들어 다시 짜면서 연속 경기일 상한을 낮춘 경우다. 입력 오류로 돌려주며 문장 예시는 §5.5에 있다.

### 1.4 경기 id

다시 짜기를 위해 경기 id는 실행이 바뀌어도 같아야 한다.

| 출처 | id | 예 |
| :--- | :--- | :--- |
| 1차 편성 취소 경기 | `M:<시리즈 번호>\|<원래 날짜>` (지금 `reschedule.js`의 `gameKey`와 같은 꼴) | `M:12\|2025-07-03` |
| 잔여 경기 | `R:<홈>-<원정>` (구단쌍당 1경기라 이것으로 유일). 구단쌍당 2경기 이상이 될 때를 대비해 `R:<홈>-<원정>-<k>`도 받는다 | `R:LG-KIA` |

재편성 기간에 다시 취소된 경기의 기록 키는 `G:<경기 id>|<그날 날짜>`다. 옛 키 `U:<묶음>|<날짜>|<차례>`는 없앤다(§5.6).

### 1.5 더블헤더

- 한 구단의 하루 경기가 2개이고, 두 경기가 **같은 홈·같은 원정**이면 그날은 더블헤더다. 한 구장은 하루 1대진이므로(DH-2), 홈이 다른 같은 구단쌍의 두 경기는 같은 날 열 수 없다.
- 더블헤더 수는 「한 대진이 같은 날 2경기를 한 날」의 수다. 두 구단 모두 상한(DH-5)에 1씩 센다.
- 따로 entity를 두지 않는다. 그래서 더블헤더를 만들고 푸는 일은 경기 1개의 날짜를 옮기는 것과 같다(§3).

## 2. 초기해: 꼭 지키는 규칙을 지키는 배정

`RescheduleInitializer.initialize(solution, seed)`. 1차 편성의 `BaseballSolutionInitializer.initialize`처럼 솔버를 돌리기 전에 부른다.

### 2.1 날짜 판(`DayGrid`)

배정 상태를 배열로 들고 있는 색인이다. 초기해, `isMoveDoable`, 진단이 함께 쓴다.

- `teamDay[t][d]`: 구단 t가 d일에 하는 경기(0~2개)
- `stadiumDay[s][d]`: 구장 s를 d일에 쓰는 홈 구단(없으면 -1). 잠실은 두 구단이 같은 칸을 쓴다
- `played[t]`: 경기한 날 비트열과 `runAtStart`. 연속 경기일 검사에 쓴다
- `dh[t]`: 더블헤더 수(`doubleHeadersUsed` 포함)

### 2.2 넣을 수 있는 날

경기 g = (홈 h, 원정 a)를 d일에 넣을 수 있는 조건:

1. **보통 경기**: h와 a 모두 d일에 경기가 없다. h의 구장이 d일에 비어 있다. h와 a 각각 d일을 넣어도 연속 경기일이 상한 이하다.
   - 연속 경기일 = d 바로 앞까지 이어진 경기일 + 1 + d 바로 뒤부터 이어진 경기일. 기간 첫날 앞쪽 값은 `runAtStart`다.
2. **더블헤더**: h와 a 모두 d일에 경기가 정확히 1개이고, 그 경기가 g와 홈·원정이 같다. 그 경기가 고정 경기가 아니다(§1.3). h와 a 모두 더블헤더 수가 상한 미만이다. 상한이 0이면 이 길은 없다. 연속 경기일은 바뀌지 않는다(더블헤더 날은 하루로 센다).

### 2.3 배정 순서

1. **들어갈 수 있는 경기 수의 상한**을 구단마다 먼저 센다. 기간의 빈 날에 연속 경기일 상한을 지키며 넣을 수 있는 최대 경기일 수를 동적 계획으로 구하고, 남은 더블헤더 수만큼 더한다. 남은 경기 수가 이 상한보다 많으면 그 차이만큼은 어떻게 해도 못 넣는다. 이 숫자는 §2.5 진단에 쓴다.
2. **가장 막힌 경기부터** 넣는다. 지금 넣을 수 있는 날이 가장 적은 경기를 먼저 고른다. 같으면 「남은 경기 ÷ 남은 빈 날」이 큰 구단의 경기를 먼저 고르고, 그래도 같으면 시드로 섞는다.
3. **날 고르기**: 남은 경기의 선택지를 가장 적게 줄이는 날(least-constraining value)을 먼저 본다. 같으면 점수 변화가 좋은 날을 고른다(현재 기준 순서로 사전식 비교). 위쪽 후보 몇 개 중에서 시드로 고른다(GRASP).
   - 보통 경기를 먼저 보고, 넣을 날이 없을 때만 더블헤더를 본다. 기준 5(더블헤더 최소)는 탐색이 더 다듬는다.
4. **막혔을 때 수리**: 넣을 날이 없으면 고정되지 않은 경기 1~2개만 막고 있는 날을 찾는다. 그 경기를 빼고 g를 넣은 뒤 뺀 경기를 다른 날에 넣어 본다. 다 들어가면 받아들이고, 아니면 되돌린다. 깊이는 2, 시도 횟수에도 상한을 둔다.
5. 그래도 안 되면 g는 비워 둔다(`day = null`).

여러 번 시작: 한 번에 수 밀리초이므로 시드마다 약 30번 돌린다. 못 넣은 경기가 가장 적은 결과를 고르고, 같으면 점수가 높은 결과를 고른다. 어느 결과든 꼭 지키는 규칙 위반은 0이다(§6.3에서 검사).

### 2.4 기간 검사(입력)

- 기간 시작은 **1차 편성 마지막 날의 다음 날 이후**여야 한다. 1차 편성 경기는 모두 기간 앞의 경기로 다룬다(§1.2). 시작이 그보다 이르면 실행하지 않는다.
- 마감일은 시작일 이후다. 기간 길이에도 상한(예: 120일)을 둔다. 탐색 크기를 묶기 위해서다.
- 1차 마지막 날 다음 날과 시작일 사이의 날은 경기 없는 날이다. 연속 경기일이 끊기고, 이동은 그대로 이어서 센다.

### 2.5 못 넣은 경기와 이유

**진단은 최종 결과(탐색이 끝난 가장 좋은 해)에 한다.** 초기해에서 못 넣은 경기 중 탐색이 넣은 것이 있을 수 있기 때문이다. 과정은 `RescheduleDiagnosis.explain(solution)` 하나다.

1. **날짜마다 막힌 이유**: 못 넣은 경기 g에 대해 기간의 날마다 §2.2를 검사하고, 첫 번째로 걸린 이유를 적는다.

   | 코드 | 이유 |
   | :--- | :--- |
   | `TEAM_BUSY` | 홈이나 원정 구단이 그날 다른 경기를 한다(상대와 함께 적는다) |
   | `STADIUM_BUSY` | 그 구장에서 그날 다른 대진이 열린다(잠실: 다른 잠실 구단의 홈 경기) |
   | `RUN_LIMIT` | 넣으면 그 구단의 연속 경기일이 상한을 넘는다(이어지는 날짜 구간을 함께 적는다) |
   | `DH_LIMIT` | 더블헤더로만 넣을 수 있는데 상한에 걸린다(또는 상한 0) |
   | `PINNED_DAY` | 더블헤더로만 넣을 수 있는데 그날 경기가 발표한 경기다 |
   | `SEARCH` | 그날은 막힌 이유가 없는데 다른 경기와 맞물려 넣지 못했다 |

2. **구단 상한**: §2.3의 1번 상한을 넘은 구단이 있으면 그것이 가장 분명한 이유이므로 맨 앞에 둔다.
3. **고칠 곳**: 꼭 지키는 규칙을 하나씩 조금 풀어 초기해만 다시 만들어 본다(각 수십 밀리초).
   - 마감일 +1일, +2일, … +14일 중 다 들어가는 가장 짧은 값
   - 연속 경기일 상한 +1
   - 더블헤더 상한 +1
   
   다 들어가는 것이 **실제로 만들어진** 경우만 「~하면 모두 들어갑니다」라고 쓴다. 못 만들었으면 「~해 보세요」라고만 쓴다. 엔진은 이 값을 스스로 적용하지 않는다(요구 §9).
4. **화면 문장**은 서버가 만든다. 개발 용어 없이 요구 §9의 예시 꼴로 쓴다.

   | 경우 | 문장 틀 |
   | :--- | :--- |
   | `RUN_LIMIT`가 가장 많음 | 「{홈}–{원정} 1경기를 넣을 날이 없습니다. {구단}이 {날짜}~{날짜} 매일 경기라 연속 경기일 상한({n}일)에 걸립니다.」 |
   | `TEAM_BUSY` | 「{구단}은 남은 날마다 이미 경기가 있습니다.」 |
   | `STADIUM_BUSY` | 「{구장}에서 남은 날마다 다른 경기가 열립니다.」 |
   | `DH_LIMIT` | 「더블헤더로만 넣을 수 있는데 {구단}의 더블헤더가 이미 {n}번입니다.」 |
   | 구단 상한 | 「{구단}은 이 기간에 최대 {n}경기만 할 수 있는데 {m}경기가 남았습니다.」 |
   | `SEARCH` | 「넣을 자리는 있었지만 다른 경기와 맞물려 넣지 못했습니다. 다시 실행하거나 실행 시간을 늘려 보세요.」 |
   | 고칠 곳(확인됨) | 「→ 마감일을 {날짜}로 {k}일 늦추면 모두 들어갑니다」 / 「→ 연속 경기일 상한을 {n}일로 늘리면 모두 들어갑니다」 |
   | 고칠 곳(확인 못 함) | 「→ 마감일을 늦추거나 더블헤더 상한을 늘려 보세요」 |

## 3. 이동(move)과 `isMoveDoable`

모든 이동은 `GameDayMove(type, games, targets)` 하나로 표현한다. 「경기 목록 → 새 날짜 목록」이며, 1차 편성의 `SeriesReassignmentMove`와 같은 꼴이다. 공장(factory)마다 후보를 만들고, 무작위 순회는 기존 `SamplingMoveIterator`를 그대로 쓴다. 고정 경기는 어느 공장도 고르지 않는다.

| # | 이동 | 내용 | 주로 좋아지는 것 |
| :--- | :--- | :--- | :--- |
| M1 | 옮기기(shift) | 경기 1개를 다른 날로 옮긴다. 비어 있던 경기를 날에 넣는 것도 포함한다. 더블헤더 한 경기를 옮기면 더블헤더가 풀린다 | 모든 기준 |
| M2 | 맞바꾸기(swap) | 두 경기의 날짜를 맞바꾼다 | 이동 거리, 마지막 경기일 |
| M3 | 더블헤더 만들기 | 경기를 같은 홈·원정 경기의 날로 옮겨 더블헤더로 만들고, 그 경기가 쓰던 날을 비운다 | 연속 경기일 여유, 마지막 경기일 |
| M4 | 빼고 넣기(eject-insert) | 비어 있는 경기 g를 d일에 넣고, 막고 있는 경기 1~2개를 다른 넣을 수 있는 날로 옮긴다. 못 넣은 경기 수가 줄어드는 때만 만든다 | 못 넣은 경기(Hard 2단계) |
| M5 | 두 날 사이 체인(Kempe chain) | d1과 d2 사이에서 같은 구단을 공유하는 경기를 이어 그 묶음을 통째로 맞바꾼다. 묶음이 두 날 전부이면 「날 맞바꾸기」다. 묶음이 고정 경기에 닿으면 만들지 않는다. 구단 하루 1경기와 구장 하루 1대진이 저절로 지켜진다 | 월요일 경기, 마지막 경기일, 이동 |

- 경기를 비우는 이동(날 → 비어 있음)은 만들지 않는다. Hard 2단계를 나쁘게 하는 이동이라 쓸모가 없다.
- 공장마다 뽑히는 비율은 설정 파일에서 정하고, 구현 중 벤치로 맞춘다(§7).

### 3.1 `isMoveDoable`에서 막는 것

`DayGrid`(§2.1)를 단계마다 한 번 만들고, 이동이 건드린 구단과 날만 검사한다.

| 규칙 | 검사 |
| :--- | :--- |
| DH-1 구단 하루 1경기 | 건드린 날마다 구단 경기 수 ≤ 1이다. 2이면 같은 홈·원정이어야 한다. 3은 없다 |
| DH-2 구장 하루 1대진 | 건드린 날마다 구장(잠실 공유)의 홈 구단은 1개다. 더블헤더는 한 대진이다 |
| DH-3 기간 안 | value range가 기간의 날뿐이라 저절로 지켜진다. 비어 있는 경기는 Hard 2단계로 센다 |
| DH-4 연속 경기일 | 건드린 구단마다 건드린 날 둘레의 연속 경기일 ≤ 상한이다(`runAtStart` 포함) |
| DH-5 더블헤더 상한 | 건드린 구단의 더블헤더 수 ≤ 상한이다(`doubleHeadersUsed` 포함) |
| 고정 | 고정 경기를 옮기지 않는다. 발표한 경기에 붙는 더블헤더를 만들지 않는다 |
| M4 | 적용 뒤 못 넣은 경기 수가 줄어든다 |

이 검사를 통과한 이동만 점수 계산으로 간다. 그래서 Hard 1단계는 탐색 내내 0이고, 남는 것은 채점기 쪽의 안전망뿐이다.

### 3.2 솔버 설정

`rescheduleSolverConfig.xml`(새 파일):
- `solutionClass` = `RescheduleSolution`, `entityClass` = `RGame`
- `easyScoreCalculatorClass` = `RescheduleEasyScoreCalculator`
- Late Acceptance(크기는 400부터 시작해 벤치로 정함), `acceptedCountLimit` 소수
- `unionMoveSelector`에 M1~M5 공장
- `moveThreadCount`는 쓰지 않는다. 시드마다 단일 스레드 솔버를 병렬로 돌리는 `MultiStartSolver` 방식을 그대로 쓴다
- 기본 실행 시간 10초, 개선 없음 3초. 문제가 작아 몇 초 안에 수렴할 것으로 본다. 벤치로 확인한다

## 4. 점수 단계

### 4.1 단계 구성

| 단계 | 내용 | 정상 결과 |
| :--- | :--- | :--- |
| Hard 1 | 꼭 지키는 규칙 위반 수: DH-1, DH-2, DH-4, DH-5(날·구단마다 넘은 만큼) | 언제나 0. 초기해와 `isMoveDoable`이 막고, 채점기는 안전망이다 |
| Hard 2 | 못 넣은 경기 수(DH-3) | 0이 목표. 0이 아니면 §2.5 진단 |
| Soft 1~6 | 요구 §5의 기준 5개를 사용자가 정한 순서로. 「이동 공정성」만 두 단계(횟수, 거리)를 붙여 쓴다 | 작을수록 좋다 |

점수 문자열 예: `[0/0]hard/[0/-1200/-35000/-52340/-4/-2]soft`

### 4.2 기준 순서를 바꾸는 법

`ScoreSettings.objectiveAt`과 같은 방식이다.

```java
// 기준(사용자가 고르는 단위)
LAST_DAY, FAIRNESS, ADDED_DISTANCE, MONDAY, DOUBLE_HEADER
// 점수 단계(채점 단위): FAIRNESS만 둘로 펼친다
LAST_DAY, FAIR_MOVES, FAIR_DISTANCE, ADDED_DISTANCE, MONDAY, DOUBLE_HEADER

RescheduleSettings.of(String[] order, ...)   // order = ["lastDay","fairness","addedDistance","monday","doubleHeader"]
int levelAt(int softLevel)                    // 1~6 → 위 점수 단계 중 하나
```

- 순서를 펼칠 때 `fairness`는 두 단계를 차지한다. 두 단계 안의 순서(횟수가 먼저인지 거리가 먼저인지)는 **고른 1차 버전의 운영 방침**에서 `moves`와 `distance` 중 앞선 것을 먼저 쓴다. 1차 버전에 운영 방침(`settings.objective`)이 없으면 횟수를 먼저 쓴다. 이 둘을 따로 떼어 순서를 바꾸게 하지는 않는다. 요구 §5에서 둘은 하나의 기준이기 때문이다.
- 순서 배열은 5개 기준이 빠짐없이 한 번씩이어야 한다. 아니면 입력 오류다(`ScoreSettings.ofObjectives`와 같은 검사).

### 4.3 기준별 계산

| 점수 단계 | 계산 | 범위 |
| :--- | :--- | :--- |
| `LAST_DAY` | 구단마다 마지막 경기일 Lₜ를 구한다(기간 안의 고정·배정 경기, 없으면 `lastPlayedDay`). 벌점 = Σ₍ᵢ<ⱼ₎ max(0, \|Lᵢ − Lⱼ\| − 허용 일수)² | 시즌 전체 |
| `FAIR_MOVES` | 구단별 이동 횟수 = `baseMoves` + 기간 이동 횟수. 벌점 = `ScoreFormulas.scaledGapPenalty(횟수, moveGap)` | 144경기 |
| `FAIR_DISTANCE` | 구단별 이동 거리 = `baseDistanceTenths` + 기간 이동 거리. 벌점 = `ScoreFormulas.distanceGapPenalty(거리, distanceGapTenths)` | 144경기 |
| `ADDED_DISTANCE` | 모든 구단의 기간 이동 거리 합(0.1km 단위). 출발 구장에서 첫 경기로 가는 길도 포함한다 | 재편성 부분 |
| `MONDAY` | 기간 안 월요일 경기 수. 더블헤더는 2경기다 | 재편성 부분 |
| `DOUBLE_HEADER` | 기간 안 더블헤더 수(대진-날 수) | 재편성 부분 |

- **마지막 경기일**: 모든 쌍이 허용 일수 이내라는 것은 「가장 늦게 끝나는 구단 − 가장 먼저 끝나는 구단 ≤ 허용 일수」와 같다. 쌍마다 넘은 만큼의 제곱을 더하는 이유가 있다. 양 끝만 보면 점수 판이 평평해서, 탐색이 어느 쪽으로 가야 좋아지는지 모른다. 쌍마다 보면 가운데 구단을 옮겨도 점수가 움직인다. 기존 공정성 벌점(`scaledGapPenalty`)과 같은 꼴이다.
- **허용 차이**는 고른 1차 버전의 운영 방침 값(`settings.objective.moveGap`, `distanceGapKm`)이다. 운영 방침이 없는 예전 버전이면 `ProblemCodec`의 기본값(이동 4회, 600km)을 쓴다.
- 못 넣은 경기는 Soft 계산에 들어가지 않는다. Hard 2단계가 먼저이므로 문제 되지 않는다.

### 4.4 재편성 부분의 이동 계산

구단마다 기간 안의 경기를 날짜순으로 늘어놓는다(고정 경기 포함, 더블헤더 날은 하루).

```
prev = startStadium
for 경기한 날 d (날짜순):
    s = 그날 구장(홈 구단의 구장)
    거리 += dist(prev, s)          // 쉬는 날이 3일 이상이어도 그대로 센다(결정 15)
    if s != prev: 이동 횟수 += 1    // 구장이 다를 때만. 잠실 두산↔LG는 같은 구장
    prev = s
```

- 1차 편성의 `LONG_BREAK_REST_DAYS`(3일 이상 쉬면 0km)는 기간 앞의 1차 부분에만 쓴다(§1.2). 1차 마지막 연전에서 재편성 첫 경기로 가는 길도 재편성 규칙을 따른다. 그래서 그 사이가 길어도 거리를 센다(요구 §6).
- 이동 횟수를 거리 > 0이 아니라 구장 번호로 센다. 그래도 지금 거리표에서는 같은 구장일 때만 거리가 0이라 1차 편성의 셈과 어긋나지 않는다.

### 4.5 다시 짤 때 이동

- 이미 치른 재편성 경기는 기간 앞의 경기로 접는다(§1.2).
- 기간 안에서 취소된 재편성 경기의 원래 날은 **이동 계산에서 뺀다**(그날 경기하지 않은 것으로 본다). 결정 10은 1차 편성 부분만 정했고, 재편성 부분은 §8.1의 1번으로 정했다.

### 4.6 채점기: Easy만 쓰는 이유

AGENTS.md의 1차 편성은 Bavet(실제 솔버)과 Easy(교차 확인)를 함께 쓴다. 재편성은 **`RescheduleScoreFormulas.evaluate` 하나를 Easy 채점기로 쓴다.**

- 크기가 작다. 배정 경기는 약 75개이고, 고정 경기를 합쳐도 150개 이하다. 날은 20~60일이다. 한 번 채점은 「경기를 구단 × 날 판에 놓고 구단마다 날을 한 번 훑기」라 약 10 × 60칸이다. 수 마이크로초로 예상하며, 초당 수십만 번 채점할 수 있다.
- 기준이 대부분 「구단마다 날짜순 경로」다. Bavet으로 쓰면 1차 편성처럼 사용자 정의 collector가 필요해서, 두 구현을 맞추는 비용만 늘어난다.
- 교차 확인은 테스트 쪽의 **따로 쓴 단순 채점기**(`RescheduleReferenceScorer`, §6.1)가 맡는다.
- 측정에서 느리면, 바뀐 두 구단만 다시 세는 `IncrementalScoreCalculator`로 바꾼다. 같은 `RescheduleScoreFormulas`를 쓰므로 바꿔도 parity 테스트는 그대로다.

위 예는 **다시 짜는** 요청이다. 처음에는 9/1부터 짰다. 9/5에 넣은 LG–KIA 취소 경기가 다시 취소되었고, 9/8부터 다시 짠다. 처음 짤 때는 `reschedule.plan`이 비어 있고, `games`에 `G:` 기록이 없다.

- `problem`의 위쪽(`teams`부터 `games`까지)은 **고른 1차 편성 버전의 프로젝트 그대로**다. `plan`은 모든 시리즈가 배정되어 있어야 한다.
- `reschedule.targets`: 배정 대상 목록이다. 화면이 지금처럼 브라우저 코어로 만들어 보낸다(취소 표시 + 잔여 경기 + 홈 73/71 나누기). 서버는 다시 만들지 않고 **검사만** 한다. 이렇게 하면 화면에 보인 「배정 대상 75경기」와 엔진이 푼 문제가 언제나 같다. 홈 나누기(`fitHomeTotals`)를 Java로 한 번 더 옮겨 두 구현을 맞출 일도 없다.
  - 취소 대상마다 그 시리즈의 날짜가 맞는지, 그 경기에 취소 표시(`games`)가 있는지 본다. 홈·원정은 시리즈 그대로여야 한다(결정 1).
  - 1차 편성의 취소 경기는 모두 정확히 한 번씩 들어 있어야 한다.
  - 구단쌍마다 1차 편성 경기 + 잔여 대상 = `settings.gamesPerPair`(16)이어야 한다.
  - `homeTotals`가 있으면 구단마다 「1차 홈 + 잔여 홈 = 목표」여야 한다.
- `reschedule.plan`: **고정할** 재편성 일정이다. 처음 짤 때는 비어 있다. 다시 짤 때는 화면이 그 버전의 발표 일정을 보낸다. 서버는 항목마다 이렇게 다룬다.
  - 날짜가 기간 시작 전이고 취소 기록(`G:` 키)이 없음 → 치른 경기. 기간 앞으로 접는다
  - 날짜가 기간 안이고 취소 기록이 없음 → 발표한 경기. 고정 entity가 된다
  - 그 날짜에 취소 기록이 있음 → 다시 배정할 경기(빈 날에 넣는다)
  - `plan`에 없는 대상 → 배정할 경기
- 지금 `reschedule.js` 설정 가운데 `allowMonday`, `allowDoubleHeader`, `blackouts`(경기 없는 날), RH-3은 **가져오지 않는다.** 새 요구에서 월요일은 늘 허용하고 Soft로 줄인다. 더블헤더를 끄려면 상한을 0으로 둔다.
- 결과를 다시 짜는 일은 「같은 요청에 `plan`과 `games`만 바뀐 것」이다. 엔진은 언제나 「기간 + 대상 + 고정」 하나만 다룬다(요구 §3).

### 5.6 브라우저 쪽 영향

- **`ui/show/fixtures/`는 바뀌지 않는다.** 쇼케이스(`/`, `/compare`, `/r/<id>`)는 재편성을 쓰지 않는다.
- `ui/core/README.md`의 REST 계약 표를 고친다: `plan` 모양 `[{ game, date }]`, Hard 2단계·Soft 6단계 이름, `unplaced`·`metrics`.
- `ui/core/reschedule.js`를 새 방식으로 바꾼다. 묶음(`units`, `chunk`, `buildUnits`, RH/RS)을 없애고, 대상 목록 만들기(`computeTargets`, `fitHomeTotals`)는 그대로 둔다. 채점기와 서버 없이 쓰는 간단한 배정기는 §6.4의 선택에 따른다.
- **저장된 프로젝트 옮기기**: 옛 `project.reschedule.units`, `plan: [{ unit, start, dh }]`, `games`의 `U:` 키 기록은 새 모양으로 바꿀 수 없다(묶음이 날짜 단위가 아니다). 불러올 때 이렇게 정리한다.
  - `start`와 `end`만 남기고 나머지 옛 재편성 값은 지운다.
  - `maxDoubleHeaderPerTeam`(옛 기본 3)은 버리고 새 기본값 2를 쓴다.
  - 1차 편성 경기의 취소 기록(`M:` 키)은 그대로 둔다.
  
  옛 재편성 결과는 시험용 임시 기능의 결과였으므로 지워도 된다고 본다.
- 결과를 서버에 저장해 공유 링크(`/r/<id>`)로 내는 것은 이번 범위가 아니다(요구 §10 「다음으로 미루는 것」과 같은 결). 재편성 결과는 스튜디오의 그 버전에 함께 저장한다. 서버는 메모리 캐시에만 둔다.

### 5.7 웹 계층 일반화 (가장 큰 작업)

지금 웹 계층은 `BaseballSolution`에 묶여 있다. 그리고 `JobManager.submit`과 `/score`가 `mode`가 INITIAL이 아니면 거절한다.

| 파일 | 바꿀 것 |
| :--- | :--- |
| `MultiStartSolver` | `MultiStartSolver<S>`로 일반화한다. `Sink.best(S, …)`, `Result<S>`. 시드별 단일 스레드 솔버, 병렬 실행, 가장 좋은 해 고르기는 그대로다. 재생 기록(`SolveTrace`)은 재편성에서 쓰지 않는다(`null`) |
| 새 `SolveMode` | 모드마다 다른 것을 묶는 인터페이스: 입력 검사, 캐시 키, 시드별 문제 만들기와 초기해, 솔버 설정, `best`/`done` 응답 만들기. 구현은 `InitialMode`(지금 `JobManager`의 해당 코드를 옮김)와 `RescheduleMode` |
| `JobManager` | 큐, IP당 1작업, 지켜보지 않는 작업 빼기, 캐시는 그대로 두고 모드별 일을 `SolveMode`에 맡긴다. 캐시 키에 `mode`를 넣는다. RESCHEDULE은 `ResultStore`에 저장하지 않는다 |
| `SolveOptions` | `mode`가 `INITIAL` 또는 `RESCHEDULE`인지 검사한다. RESCHEDULE의 기본 시간은 10초, 개선 없음은 3초 |
| `SolveJob` | 바꿀 것 없음(JSON만 다룬다) |
| `BaseballWebServer` | 머리 주석의 API 표, `/score`의 모드 나누기. 재편성 채점은 `RescheduleScoreFormulas`를 바로 부른다(Easy라 `SolutionManager`가 필요 없다) |
| 새 `RescheduleCodec` | 요청 → `RescheduleSolution`(대상 검사, `TeamHistory` 만들기, 고정 나누기), 해 → `plan`/`metrics` JSON |
| 새 `RescheduleDiagnosis` | §2.5 |

모드를 클래스 하나에 `if`로 섞지 않고 인터페이스로 나눈다. 1차 편성 코드의 동작은 그대로이고 옮기기만 하므로, 지금 있는 서버 테스트가 그대로 통과해야 한다.

## 6. 테스트 계획

### 6.1 점수 parity

- **`RescheduleScoreParityTest`**: 무작위 배정(규칙을 어긴 것, 비어 있는 경기, 더블헤더, 고정 경기, 다시 짜기 상태 포함) 수백 개를 만든다. `RescheduleScoreFormulas.evaluate`(Easy)와 `RescheduleReferenceScorer`가 8단계 모두 같아야 한다.
  - `RescheduleReferenceScorer`는 테스트 소스에만 둔다. 배열이나 캐시 없이, 요구 §4~§6 문장을 그대로 옮긴다. 구단마다 경기 목록을 날짜순으로 정렬해 센다. **같은 계산식을 공유하지 않는 것이 목적이다.**
- **`FirstRoundBaseTest`**: 2025 기본 1차 편성에서 `TeamHistory.baseMoves`와 `baseDistanceTenths`가 `ScoreFormulas.summarizeTeam`과 같아야 한다. 취소 경기가 있어도 값이 그대로이고, `runAtStart`만 줄어야 한다(§1.2의 「두 가지로 세기」).
- **기준 순서**: 같은 배정을 순서만 바꿔 채점하면 단계 값이 그 순서대로 자리를 바꿔야 한다. `fairness`는 두 단계가 붙어서 움직인다.

### 6.2 이동 계산

손으로 만든 작은 예로 확인한다.
- 3일 이상 쉰 뒤의 재편성 이동은 거리를 센다. 1차 부분의 올스타 휴식기는 0이다.
- 출발 구장은 1차 원래 일정의 마지막 연전 구장이다. 그 연전이 취소되었어도 같다.
- 잠실 두산↔LG는 이동 0회, 0km다.
- 더블헤더 날은 이동 1번이다.
- 다시 짤 때 취소된 재편성 경기의 원래 날은 경로에서 빠진다.

### 6.3 꼭 지키는 규칙

- **초기해**: 2025 기본 1차 편성 + 무작위 취소 30경기 + 기간 4주로 시드 20개를 돌린다. 모두 Hard 1단계가 0이고 못 넣은 경기가 0이어야 한다.
- **이동**: `FULL_ASSERT`로 짧게 돌린다. 공장마다 무작위 이동 수천 개에서 `isMoveDoable`이 받아들인 것을 적용한 뒤 Hard 1단계가 0이어야 한다. 받아들이지 않은 것에는 실제로 규칙 위반이 있어야 한다(지나치게 막지 않는지 확인).
- **다시 짜기**: 발표한 경기의 날짜가 결과에서 그대로다. 새 취소 경기만 비었던 날에 들어간다. 연속 경기일과 출발 구장은 치른 경기를 이어서 센다.
- **못 넣은 경기**: 기간을 일부러 좁힌 예에서 다음을 확인한다.
  - (a) 구단 상한 문장이 나온다.
  - (b) 「마감일 +k일」 고칠 곳이 확인됨으로 나오고, 실제로 그 마감일로 돌리면 다 들어간다.
  - (c) 엔진이 입력 값을 바꾸지 않았다.

### 6.4 브라우저 채점기와 배정기 (결정: A)

AGENTS.md에 따르면 스튜디오는 `file://`로 열어도 동작해야 한다. 그 경우 `MockEngineAdapter`가 브라우저 Worker에서 `KBO.Reschedule.createSearch`를 부른다. 사용자가 **A**를 골랐다. `reschedule.js`에 서버와 같은 계산식의 채점기와, 초기해(§2) 수준의 탐욕 배정기를 둔다. 탐색은 서버보다 약하다.

**사용자가 짚은 주의점**: 서버와 브라우저의 계산이 조금이라도 어긋나면 오류가 된다. 같은 일정인데 점수, 평가 숫자, 규칙 위반, 못 넣은 이유가 다르게 나오면 안 된다. 그래서 다음을 지킨다.

| # | 막는 것 | 방법 |
| :--- | :--- | :--- |
| 1 | 같은 것을 두 곳에서 따로 만들기 | 배정 대상 목록(취소 + 잔여 + 홈 나누기)은 **브라우저에서만** 만들고, 서버는 검사만 한다(§5.1). 서버와 브라우저가 따로 만드는 것은 채점, 규칙 검사, 못 넣은 이유 문장 세 가지뿐이다 |
| 2 | 채점·평가 숫자·문장이 어긋남 | **같은 사례 파일을 양쪽이 푼다.** 입력 사례는 `ui/core/test/golden/reschedule-cases/`에 둔다. Java가 각 사례의 답(점수 8단계, 평가 숫자, 규칙 위반, 못 넣은 이유의 코드와 문장)을 `reschedule-golden.json`에 쓰고, `node ui/core/test/run-tests.js`가 브라우저 쪽 답과 **글자 하나까지** 비교한다. 다시 만들 때는 `mvn -q test -Dtest=RescheduleGoldenTest -Dgolden.write=true` |
| 3 | 사례가 빠진 곳에서 어긋남 | 사례에 반드시 넣을 것: 더블헤더, 잠실 두 구단, 월요일, 3일 이상 쉰 뒤 이동, 1차 취소 경기(이동은 원래대로, 연속 경기일에서는 쉬는 날), 발표 일정 고정, 다시 짜기(치른 경기·다시 취소된 경기), 못 넣은 경기, 연속 경기일 상한 경계(6일과 7일), 더블헤더 상한 0, 기준 순서 바꾸기, 운영 방침이 없는 예전 1차 버전. 무작위 배정 수십 개도 함께 넣는다 |
| 4 | 결과 모양이 어긋남 | Java 테스트가 서버 `done` 결과 견본(§5.3 모양)을 golden 폴더에 쓴다. 브라우저 배정기의 결과가 같은 항목과 같은 형(숫자/문자/배열)을 가지는지 `run-tests.js`가 비교한다 |
| 5 | 브라우저 배정기가 규칙을 어김 | `run-tests.js`가 사례마다 브라우저 배정기를 시드 여러 개로 돌린다. 결과를 2번으로 서버와 같다고 확인된 채점기로 다시 채점해, 꼭 지키는 규칙 위반이 0인지 본다 |
| 6 | 실제로 쓰다가 생긴 어긋남 | 스튜디오가 재편성 결과를 보일 때마다 브라우저 채점기로 다시 채점해, 결과에 실려 온 점수와 비교한다. 다르면 콘솔 오류를 남긴다. 그러면 `data-errors`가 0이 아니게 되어 점검(`checkall.sh`)이 실패한다. 서버가 있으면 브라우저에서 만든 결과도 `/api/v1/score`로 한 번 더 확인한다 |
| 7 | 품질 차이를 오류로 착각 | 결과에 `engine: "server"` 또는 `"browser"`를 싣는다. 브라우저에서 만든 결과에는 화면에 「인터넷 연결 없이 만든 간단한 결과입니다. 연결된 상태에서 다시 실행하면 더 다듬어집니다」를 보인다. 고칠 곳 확인(§2.5의 3)은 서버만 한다. 브라우저 결과에는 「~해 보세요」 꼴만 쓴다 |
| 8 | 규칙을 한쪽만 고침 | AGENTS.md의 「점수 계산식은 여러 곳에 있다」 항목에 재편성을 더한다: `RescheduleScoreFormulas`, `RescheduleReferenceScorer`, `RescheduleDiagnosis`의 문장, `ui/core/reschedule.js`, golden을 함께 고친다 |

배정기의 **배정 결과**는 서버와 같을 필요가 없다. 탐색이 다르기 때문이다. 같아야 하는 것은 「같은 일정을 넣었을 때 나오는 점수, 숫자, 위반, 문장」이다.

### 6.5 서버

- `/api/v1/solve` RESCHEDULE: SSE `done` 모양(§5.3), 캐시(같은 입력 → 같은 결과, INITIAL과 섞이지 않음), IP당 1작업

### 7.1 순서와 크기

- 화면(요구 §10의 결과 화면 다섯 가지와 달력에서 취소 표시)은 이 표에 넣지 않았다. 6번이 끝난 뒤 기본안 1개 + 대안 2~3개를 별도 worktree로 만든다. 별도로 약 2~3일이다.

### 7.2 위험 요소

| 위험 | 내용 | 대응 |
| :--- | :--- | :--- |
| 기간이 좁아 다 들어가지 않는 경우가 흔함 | 마감일이 빠르면 연속 경기일 6일 상한 때문에 남은 경기가 많은 구단이 먼저 막힌다 | 구단 상한 계산(§2.3)으로 분명한 이유를 먼저 보이고, 고칠 곳 확인으로 숫자를 준다 |
| 고칠 곳 확인이 「안 된다」고 잘못 말함 | 확인은 탐욕 배정이라 실제로는 되는데 못 찾을 수 있다 | 확인된 것만 「들어갑니다」라고 쓰고, 나머지는 「해 보세요」로 쓴다 |
| 공정성 때문에 먼 원정이 늘어남 | 공정성이 늘어난 이동 거리보다 위라서, 1차의 차이를 메우려고 이동이 적은 구단에 먼 원정을 넣는다(결정 6에서 알고 받아들인 것) | 허용 차이 안에 들어오면 3번 기준이 줄인다. 평가 숫자에 늘어난 거리를 구단별로 보인다 |
| 1차 차이가 처음부터 커서 공정성이 허용 안에 못 들어옴 | 재편성은 9~15경기뿐이라 135경기의 차이를 다 메우지 못할 수 있다. 그러면 2번 기준이 끝까지 0이 되지 않는다 | 정상 동작이다. 평가 숫자에 「1차에서 이미 난 차이」를 함께 보이는 것을 화면 설계에서 다룬다 |
| 마지막 경기일 1순위가 모두를 마감일로 미룸 | 요구 §5대로 「같이 끝나기」만 본다. 경기가 적은 구단은 오래 쉴 수 있다 | 요구에 적힌 대로다(최대 연속 휴식일은 이번 범위 밖). 결과 표에서 쉬는 날이 보인다 |
| Easy 채점 속도 | 예상(수 마이크로초)이 틀릴 수 있다 | 4번 벤치에서 잰다. 느리면 증분 채점기로 바꾼다(§4.6) |
| 다시 짜기 입력이 어긋남 | 화면이 보내는 대상, 발표 일정, 취소 기록이 서로 맞지 않을 수 있다 | 서버가 모두 검사하고(§5.1) 쉬운 문장으로 돌려준다 |
| 홈 73/71이 맞지 않음 | 1차 편성 홈 수에 따라 잔여 경기 홈을 목표대로 나눌 수 없을 수 있다(`fitHomeTotals`의 `ok: false`) | 실행하지 않고, 목표와 다른 구단과 그 경기 수를 보인다(§8.1의 2번) |
| 웹 계층을 옮기다 1차 편성이 깨짐 | 5번은 지금 동작하는 서버 코드를 옮긴다 | 옮기기와 새 모드 추가를 따로 커밋하고, 옮긴 직후 전체 테스트와 스튜디오 점검을 돌린다 |
