# KBO 솔버 시드 4 vs 8(서버 4코어 vs 8코어) 벤치마크

측정일 2026-11-03~04. 러너 [`SeedCountBench`](../src/main/java/org/optaplanner/examples/baseball/web/SeedCountBench.java), 입력 생성 [`seed-count-problems.js`](../scripts/seed-count-problems.js), 실행 [`seed-count-bench.sh`](../scripts/seed-count-bench.sh), 집계 [`seed-count-summary.py`](../scripts/seed-count-summary.py). 앞선 측정은 [ENGINE_SEED_BENCHMARK.md](ENGINE_SEED_BENCHMARK.md).

질문: 공개 서버(Akamai 도쿄 Dedicated 4 vCPU, `SEEDS=4`)를 8 vCPU로 올려 시드 8개를 병렬로 돌리면 결과가 눈에 띄게 좋아지는가.

## 1. 결론 요약

| 항목 | 결론 |
|---|---|
| 1분(편성 스튜디오) | 8시드가 전체 이동 거리를 **약 1~2% 줄인다**: 기대값 2025 −1,073km(−1.7%), 2027 −667km(−1.1%), 2028 −979km(−1.6%). 구단 하나로 치면 시즌에 70~110km. |
| 규칙·허용 차이 | 차이 없음. 실행 704개 모두 Hard 0/0. 고른 해(4시드·8시드 모두)는 허용 차이(이동 횟수 4회·이동 거리 600km·주말·공휴일 3점)를 **모든 묶음에서** 맞췄다. 지금 운영 방침에서는 갇힘이 시드 하나 기준 2~18%라 4시드로 이미 0.1% 이하가 된다(앞선 측정의 60%→20%는 예전 점수 구성 기준). |
| 나쁜 경우 | 8시드의 효과는 주로 나쁜 쪽 꼬리를 줄이는 것. 10묶음 중 가장 나쁜 묶음이 2025 65,154→62,512km, 2027 61,437→60,268km, 2028 67,612→62,806km. 기대값 기준 "나쁜 쪽 10%"는 900~1,250km 좋아진다. |

| 보여주는 문(휴대폰 첫 화면) | **해당 없음.** 첫 화면의 「직접 해보기」 편성 폼은 2026-10-23부터 숨겨져 있어(`ui/show/index.html` `#try` hidden, 운영 사이트에서 확인) 방문자가 서버 편성을 돌리는 곳은 편성 스튜디오뿐이다. 그래서 판단은 1분(스튜디오) 결과로 한다. |

## 2. 측정 방법

- **서버와 같은 경로.** `SeedCountBench`는 `web` 패키지 안에서 서버의 [`MultiStartSolver`](../src/main/java/org/optaplanner/examples/baseball/web/MultiStartSolver.java)를 그대로 부르고, 시드마다 문제를 `JobManager.problemFor`(SCRATCH)와 같이 만든다: `ProblemCodec.toSolution` → `applyPlan` → `BaseballSolutionInitializer.initialize(seed)`. 시드마다 단일스레드 솔버, 최고 점수 해를 고른다.
- **입력(세 가지).** 편성 스튜디오가 서버에 보내는 프로젝트 그대로 + 실행 버튼이 채우는 기본 운영 방침(`order: 이동 횟수 → 이동 거리 → 주말·공휴일 → 전체 이동 거리`, 허용 차이 4회·600km·3점).
  - 2025: `KBO.Preset.buildProject()`(실제 일정, 개막전 시리즈 5개 고정).
  - 2027: `KBO.Preset2027.buildProject()`(예상 일정, 개막전 시리즈 5개 고정).
  - 2028: 2027 설정에서 날짜만 2028로 옮기고 연전 기간·시리즈를 스튜디오 함수(`generateSlots`·`generateSeries`)로 새로 만든 시즌. 짝수 해라 홈 73/71·어린이날 홈 구단이 2027과 반대, 개막전 고정 없음.
  - 2023·2024 실제 일정(`data/baseball/input*.json`)은 4연전 기간이 없어 초기해 생성기가 받지 않는다(`calendar is missing the 2-game or 4-game slot`). 그래서 세 번째 입력을 2028로 했다.
  - 이 입력과 점수 구성(허용 차이 방식)은 앞선 문서(`input_2025.json` 원본, 평균 ± 허용오차)와 달라 숫자를 바로 비교할 수 없다.
- **종료 조건.** 10초는 개선 없음 종료 없음(보여주는 문의 시간 설정과 같지만 입력·점수 구성은 스튜디오 것), 60초는 편성 스튜디오(개선 없음 종료 = 시간의 절반 30초). 3분은 사용자 결정으로 재지 않았다(스튜디오 기본은 2분, 범위 1~5분).
- **8코어 흉내.** 이 컴퓨터(Apple M4, 성능 코어 4 + 효율 코어 6)에서 8개를 한 번에 돌리면 일부가 효율 코어에 올라간다. 그래서 8시드는 **4개씩 두 판**으로 돌려 시드마다 코어 하나를 쓰게 하고 두 판의 최고를 골랐다. 4시드 묶음도 한 판(4개 동시)이라 시드당 조건이 같다. 참고로 8개를 한 번에 돌린 묶음도 일부 쟀다.
- **서로 다른 시드.** 묶음마다 다른 시드: 4시드 묶음 g는 `기준+4g..`, 8시드 묶음 g는 `기준+10000+8g..`, 한 번에 8은 `기준+20000+8g..`. 기준은 조건마다 100만 단위로 다르다.
- **묶음 수.** 조건(입력 × 시간)마다 4시드 10묶음, 8시드 10묶음. 10초는 한 번에 8 참고 5묶음, 2025 60초는 3묶음.
- **보조 추정(기대값).** 4시드·8시드 판에서 나온 시드 결과(모두 4개씩 동시에 돈 것) 120개를 모아, k개를 무작위로 골라 최고를 고를 때의 정확한 기대값을 계산했다. 점수 내림차순 r번째가 최고일 확률 = C(n−r, k−1)/C(n, k). 묶음 10개는 흔들림이 커서(묶음 사이 표준편차 500~1,900km) 이 추정이 4 vs 8 차이를 더 안정적으로 보여준다.
- **"갇힘"(허용 차이 못 맞춤).** soft0~soft3(미배정, 1~3순위 목적식의 허용 차이 초과) 중 하나라도 0이 아니면 갇힘. soft4 = −전체 이동 거리(km). 화면 네 기준은 `Metrics`·`ScoreFormulas.TeamTotals`로 계산했다(이동 횟수 격차 = 최다−최소 구단, 이동 거리 격차 km, 주말·공휴일 격차 = 휴일 가중치 점수 최다−최소, 전체 이동 거리 km).
- **부하 관리.** 판마다 시작 전 1분 load average와 이 JVM 밖 프로세스 CPU 합(`ps`)을 기록하고, 250%를 넘으면 최대 20분 기다렸다. 조건(4시드 → 8시드 a → 8시드 b → 한 번에 8)을 판 단위로 번갈아 돌려 부하 변화가 한쪽에 몰리지 않게 했다. JVM마다 첫 판(예열)은 버렸다. 측정 중 다른 세션의 Chrome 탭 하나가 CPU 1개를 계속 썼다(약 100%).
- 환경: Apple M4 10코어, Java 25, OptaPlanner 9.44.0.Final, `-Xmx6g`, XML 설정 그대로(Late Acceptance, REPRODUCIBLE).

## 5. 공정성 점검

판마다 시드별 점수 계산 속도 평균(INFO 로그 `Local Search phase ended ... score calculation speed`). 같은 입력·시간에서 4시드와 8시드(4씩 두 판)의 속도가 같으면 두 조건이 같은 CPU를 받은 것이다.

| 입력·시간 | 4시드 | 8시드(4씩 두 판) | 8개 한 번에(참고) |
|---|---|---|---|
| 2025 · 60초 | 25,348회/초 | 25,049 | 14,417 |
| 2027 · 60초 | 26,222 | 25,473 | - |
| 2028 · 60초 | 31,615 | 33,536 | - |
| 2025 · 10초 | 18,349 | 17,826 | 12,262 |
| 2027 · 10초 | 9,227 | 9,172 | 7,283 |

- 4시드와 8시드(두 판)의 속도는 조건마다 6% 안쪽으로 같다. 비교는 공정하다.
- 2027 10초는 측정 중 다른 세션의 서버가 4코어로 편성하고 있어 속도가 절반 아래로 떨어진 판이 있었다(최저 2,916회/초, 기다린 판 7개). 양쪽에 고르게 걸렸지만 이 조건의 절대값은 덜 믿을 만하다.
- 8개 한 번에(참고)는 시드당 속도가 20~45% 낮고, 결과도 8시드(두 판)보다 나쁘다(2025 60초 61,557 vs 60,228km). 효율 코어 탓이며, 같은 이유로 **지금 4코어 서버에서 `SEEDS=8`로만 올리면 오히려 나빠질 수 있다**.
- 서버(Akamai, AMD EPYC) 코어 하나는 M4 성능 코어보다 느릴 수 있다. 그러면 같은 1분에 덜 나아가지만, 4 vs 8의 상대 차이는 비슷할 것으로 본다(서버에서 따로 재지는 않았다).

## 6. 비용과 판단

| 항목 | 4 vCPU(지금) | 8 vCPU |
|---|---|---|
| 요금 | 월 $72 (Dedicated 8GB) | 월 $144 (Dedicated 16GB, 미국 리전 공시가 · 도쿄 확인 필요) |
| 1분 편성 전체 이동 거리(기대값, 세 입력 평균) | 61,222km | 60,316km (−906km, −1.5%) |
| 규칙·허용 차이 | 모두 지킴 | 모두 지킴 |

- 8코어의 품질 이득은 "전체 이동 거리 1~2%, 나쁜 경우가 덜 나쁨"이다. 화면 지표(격차 세 가지)와 규칙 준수는 같다.
- 결과 품질이 아닌 이득은 재지 않았다: 8코어면 대기 줄에서 한 사람이 쓰는 시간 동안 4시드 작업 두 개를 같이 돌릴 수 있다(지금 `JobManager`는 작업을 하나씩만 돌리므로 코드를 바꿔야 한다). 사람이 몰릴 때 대기 시간이 문제라면 그것이 8코어의 더 큰 이유가 될 수 있다.
- 메모리: 8시드는 시드마다 문제 사본과 솔버를 따로 가진다. 지금 4시드에 `JAVA_XMX=5g`를 쓰므로 8시드는 16GB 서버에서 Xmx를 올려야 한다(이 측정은 `-Xmx6g`로 8개 동시 실행에 문제 없었음).

## 7. 다시 재는 법

```bash
bash deploy/build.sh
bash scripts/seed-count-bench.sh target/seedbench            # 전체(약 1시간 50분)
bash scripts/seed-count-bench.sh target/seedbench 60 2028    # 한 조건만
python3 scripts/seed-count-summary.py target/seedbench > target/seedbench/summary.md
```

출력: `rounds.tsv`(판마다 부하·기다린 시간·종료 이유), `seeds.tsv`(시드마다 점수), `groups.tsv`(묶음마다 고른 해의 화면 네 기준), `log-<해>-<초>.txt`(솔버 로그). 측정 중 다른 무거운 작업(서버 편성, Chrome 점검)을 같이 돌리지 않는 것이 좋다.
