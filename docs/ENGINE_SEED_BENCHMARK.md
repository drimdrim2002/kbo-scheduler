# KBO 솔버 시드 편차·멀티스타트 벤치마크

측정일 2026-10-20. 입력 [`input_2025.json`](../data/baseball/input_2025.json)(구단 10, 정규 슬롯 45, 시리즈 225). 러너는 [`SeedBench`](../src/main/java/org/optaplanner/examples/baseball/bench/SeedBench.java), 트레이스는 [`SolveTrace`](../src/main/java/org/optaplanner/examples/baseball/bench/SolveTrace.java).

## 1. 결론 요약

| 항목 | 결론 |
|---|---|
| 시드 편차 | 크다. 같은 설정·10초에서 총 이동거리 64,294~73,318km(범위 9,000km, 약 13%). 20시드 중 12개(60%)가 soft2(거리 편차) 또는 soft3(휴일 편차)를 0으로 못 내리고 끝난다. 이 중 10개는 soft3가 -1~-15인 경미한 갇힘, 2개(시드 2, 18)는 soft2까지 남는 심한 갇힘이다. |
| 멀티스타트 | **채택.** 같은 CPU 예산(4코어×10초)에서 단일스레드 솔버 4개를 병렬로 돌려 최고를 고르면 갇힘 60%→20%(5묶음 중 1), 거리 평균 68,097→65,878km, 최악 73,318→67,590km. 단일 실행(4 move 스레드)은 중앙값 기준 1초 안에 개선이 멈추지만, 단일스레드 실행은 8초 가까이 계속 개선된다. |
| 권장 시드 수·시간 | VM 코어 수만큼 단일스레드 솔버를 병렬로(4코어면 4개, 8코어면 8개), 각 10초. 10시드 best-of-10이면 20개 중 갇힘 0. 5초로 줄이면 best-of-4 갇힘 2/5, 평균 67,288km로 10초보다 뚜렷이 나쁘므로 시간을 깎기보다 시드 수를 늘리는 쪽이 낫다. |
| 갇힘 완화 설정 | **기본값(LA 2000, ACL 40) 유지.** 10초 동안 스텝이 400~900개뿐이라 lateAcceptanceSize 400/2000/10000은 사실상 같은 동작이고 결과도 거의 같다. acceptedCountLimit 1은 10/10 갇힘으로 훨씬 나쁘다. 갇힘은 acceptor 문제가 아니라 이웃 탐색(샘플링 커스텀 무브)과 낮은 스텝 속도 문제다. |
| 트레이스 | best 이벤트마다 {elapsedMs, score, 바뀐 시리즈[id, 이전 슬롯, 이후 슬롯]}을 JSON으로 남기는 프로토타입 완료. 10초 실행 1회가 이벤트 22개, 변경 106건, 20.8KB(헤더 17.3KB + 이벤트 3.6KB). 브라우저 재생에 충분히 작다. |

## 2. 측정 방법

- 코드: `BenchSupport`가 입력을 읽고 `BaseballSolutionInitializer.initialize(solution, seed)`로 Hard 0/0 초기해를 만든 뒤, 기존 [`baseballSolverConfig.xml`](../src/main/resources/org/optaplanner/examples/baseball/solver/baseballSolverConfig.xml)을 `SolverConfig.createFromXmlResource`로 읽어 randomSeed·moveThreadCount·솔버 termination(secondsSpentLimit)만 코드에서 덮어쓴다. XML 기본값은 바꾸지 않았다. 실험 C만 localSearch의 acceptor·forager 값을 추가로 덮어쓴다.
- 초기해 시드와 솔버 시드는 같은 값을 쓴다. 실행마다 입력을 새로 읽어 상태를 공유하지 않는다.
- 기록: `ScoreRecorder`(SolverEventListener)가 best 이벤트마다 (경과 ms, 점수)를 남긴다. 솔버는 초기해에 대해 이벤트를 내지 않으므로 초기 점수는 `SolutionManager.update`로 따로 계산했다.
- 환경: Apple Silicon 10코어, Corretto 25.0.3, OptaPlanner 9.44.0.Final, `-Xmx6g`, `-Dlogback.level.org.optaplanner=warn`, environmentMode REPRODUCIBLE. XML의 localSearch stepCountLimit 100000은 10초 안에 도달하지 않는다(실행 시간이 모두 9,999~10,009ms).
- 점수: `[h0/h1]hard/[s0/s1/s2/s3/s4]soft`. s0 미배정, s1 이동횟수 편차, s2 거리 편차, s3 휴일 편차, s4 총 이동거리(km, 음수). "갇힘"은 최종 s2≠0 또는 s3≠0. 표의 "총거리"는 -s4.
- 재현성: A·B 전체를 두 번 돌렸을 때 40개 실행 중 39개가 최종 점수까지 동일했다(단일스레드 시드 1만 시간 종료 지터로 71,654↔72,684). 아래 A·B 표는 두 번째 실행, C는 첫 번째 실행 값이다.
- 재현 명령:

```bash
mvn -q compile dependency:build-classpath -Dmdep.outputFile=target/cp.txt
java -Xmx6g -Dlogback.level.org.optaplanner=warn -cp target/classes:$(cat target/cp.txt) org.optaplanner.examples.baseball.bench.SeedBench all target/bench 10
```

모드는 `A`, `B`, `C`, `trace`, `one <outDir> <초> <시드> <moveThreadCount>`, `all`. 결과는 `<outDir>/bench-*.md`, 실행별 한 줄 `runs.tsv`, best 이벤트별 한 줄 `curves.tsv`로 남는다.

## 6. 트레이스 프로토타입

- [`SolveTrace`](../src/main/java/org/optaplanner/examples/baseball/bench/SolveTrace.java)는 `SolverEventListener`로 best 이벤트마다 직전 best 해와 현재 best 해의 match→calendar 배정을 diff해 `{elapsedMs, score, changes: [[matchId, 이전 슬롯, 이후 슬롯], ...]}`를 쌓는다. 첫 이벤트는 솔버에 넘긴 초기해와 diff한다.
- 헤더에 구단(index, name, stadium), 정규 슬롯 45개(id, 시작일, 경기 수, 주말·휴일 플래그), 시리즈 225개(id, 홈·원정 index, 경기 수, 초기 슬롯), 초기 점수를 넣어 브라우저가 이 파일만으로 재생할 수 있게 했다.
- 샘플 [`trace-sample.json`](../data/baseball/trace-sample.json): 시드 0, moveThreadCount 4, 10초.

| 항목 | 값 |
|---|---|
| best 이벤트 수 | 22 |
| 바뀐 시리즈 수(누적) | 106 (이벤트당 최대 14) |
| 파일 크기 | 20,819바이트 (헤더 17,260 + 이벤트 3,559) |
| 첫·마지막 이벤트 | 19ms, 431ms |
| 초기 점수 → 최종 | [0/0/-5101/-24/-70198] → [0/0/0/0/-68501] |

단일스레드 실행은 이벤트가 50~70개라 이벤트 부분이 10KB 안팎이 된다. 이벤트당 약 160바이트이므로 멀티스타트 4개를 모두 기록해도 100KB를 넘지 않는다. 멀티스타트 재생 UI에는 선택된 시드의 트레이스만 보내거나, 4개를 모두 보내 "경주" 형태로 보여줄 수 있다.

## 7. 권장 설정과 후속 과제

권장(플레이그라운드 1회 실행):
1. 단일스레드 솔버(moveThreadCount NONE)를 VM 코어 수만큼 병렬 실행, 각 10초, 시드는 요청마다 다르게. 가장 높은 점수의 해를 채택하고 그 실행의 트레이스를 재생한다.
2. 4코어 VM이면 4시드 best-of-4(갇힘 20%, 평균 65,878km). 8코어면 8시드로 늘린다. 10시드 best-of-10은 측정 범위에서 갇힘 0이었다.
3. 솔버 XML의 lateAcceptanceSize·acceptedCountLimit은 그대로 둔다.
4. 실행 시간을 5초로 줄이면 best-of-4 평균이 67,288km로 1,400km 나빠지고 갇힘이 2/5로 늘어난다. 시간을 줄여야 한다면 시드 수를 늘려 보상한다.

후속 과제(이 벤치 범위 밖):
- 스텝 속도. 단일스레드 점수 계산 9,275/초, 10초에 415스텝은 이 크기 문제에서 매우 느리다. 커스텀 무브 생성(KempeChain·RoundBlock)과 Bavet 제약 평가를 프로파일해 스텝 속도를 올리면 같은 시간에 더 멀리 간다.
- 심한 갇힘(시드 2·18) 탈출. 0.1~0.4초 만에 s2가 남은 채 멈추는 건 현재 무브 집합에 그 지역해를 벗어나는 이웃이 없다는 뜻이다. 멀티스타트가 이를 가려 주지만, 재시작(초기해 재생성) 또는 섭동(perturbation) 단계를 넣으면 단일 실행도 개선될 수 있다.
- 점수 가중치. 사전식 s3(휴일 편차 1)가 거리 수천 km보다 우선되는 현재 순서가 공개 서비스의 "좋은 일정" 정의와 맞는지 확인이 필요하다.
