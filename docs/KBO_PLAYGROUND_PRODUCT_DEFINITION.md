## 3. 플레이그라운드 범위

### 3.1 사용자가 만지는 손잡이 (딱 4개)
1. **공평성 허용오차 슬라이더**: 이동거리 허용오차(기본 300km), 휴일 가중치 허용오차(기본 1.5)
2. **어린이날 홈 구단 선택**: 10구단 중 5개 체크(기본: 두산·키움·한화·NC·롯데)
3. **특정 날짜 홈 불가**: 날짜 + 구단 + 사유(예: 잠실 콘서트 대관) 목록 추가·삭제
4. **시리즈 고정**: 일정판에서 시리즈 카드를 원하는 슬롯에 놓고 핀 고정(개막전·어린이날은 기본 고정)

### 3.2 공통 기능
- **다시 편성**: 손잡이를 바꾸고 누르면 서버가 돌리고, 결과를 전 결과와 나란히 비교(총 이동거리, 구단별 편차, 주말 홈 수)
- **실제 2025 일정 채점**: 실제 일정을 같은 채점기로 채점해 엔진 결과 옆에 놓는다
- **탐색 과정 재생**: §4.2
- **공유 링크**: `?p=<파라미터 해시>&seed=<n>`만으로 같은 결과를 재현한다(엔진이 재현 가능 모드 + 시드 고정). 서버는 같은 링크의 결과를 캐시한다. DB 없음
- **엑셀 내보내기**: 기존 `BaseballApp` 엑셀 생성기 재사용

### 3.3 이번 론칭에서 뺀 것
엑셀·구글시트 가져오기, 시즌 중 재편성(시즌 운영 메뉴), 설정 켜기·끄기, 스냅샷, 계정·로그인. 화면에는 "다음 버전"으로만 표시한다.

## 4. 엔진 실행 방식

### 4.1 측정값 (2026-10-20, input_2025, 기존 솔버 설정)
| 시드 | 마지막 개선 | 총 이동거리 | 비고 |
| :--- | :--- | :--- | :--- |
| 0 | 0.9초 | 68,501 km | 이후 90초 개선 없음 |
| 1 | 19.4초 | 65,896 km | |
| 2 | 0.4초 | 73,318 km | 거리·휴일 편차가 0이 안 된 채 갇힘 |
| 3 | 1.1초 | 69,259 km | |

초기해 생성은 약 0.4초에 Hard 0/0. 결론: **실행은 초 단위**이므로 실제 Java 엔진을 그대로 쓴다. 문제는 시드 편차와 갇힘이고, 멀티스타트로 푼다. 벤치마크 결과(`docs/ENGINE_SEED_BENCHMARK.md`, 브랜치 claude/zealous-euler-8ad367): 단일 실행(4스레드·10초)은 20시드 중 12개가 갇히고 1초 안에 개선이 멈춘다. 단일스레드 솔버 4개를 10초 병렬로 돌려 최고를 고르면 갇힘 5묶음 중 1개, 평균 65,878km, 최악 67,590km. 10시드면 갇힘 0. 5초로 줄이면 뚜렷이 나빠진다. LA 크기·acceptedCountLimit 조정은 효과 없음.

### 4.2 멀티스타트 + 트레이스 녹화·재생
- 서버는 한 요청에 VM 코어 수만큼의 시드(4코어면 4, 8코어면 8)를 각각 **단일스레드로 10초** 병렬 실행하고 최고 해를 고른다. 시드는 요청마다 다르게 하되 공유 링크에 담아 재현한다.
- 실행 중에는 시드별 best 점수를 SSE로 흘려 보내 **N개 탐색의 경주** 화면을 만든다(실시간, 몇 초).
- 끝나면 최고 해의 **트레이스**(개선 이벤트마다 경과 ms, 점수, 바뀐 시리즈와 이전·이후 슬롯)를 함께 돌려준다.
- 브라우저는 트레이스를 20~40초로 늘려 재생한다. 속도 조절·일시정지·한 스텝씩. 화면은 왼쪽 일정판(카드 이동), 오른쪽 점수 곡선(소프트 5단계가 차례로 0이 되고 총거리가 내려감), 아래 한 줄 해설("켐페 체인: LG·두산 7라운드↔12라운드 교환").
- 기본 조건의 트레이스는 서버에 미리 만들어 두어 첫 화면이 즉시 뜬다.

**구현 메모 (2026-10-20, 탐색 과정 재생기)**
- 상태 계산은 `ui/core/replay-model.js`(`KBO.ReplayModel.build(trace)`, 순수 모듈·Node 테스트 3개)가 한다: 이벤트 i까지 적용한 시리즈→슬롯 배정과 슬롯 안 줄 번호, 누적 이동 수, 소프트 단계 절댓값, 해설 문자열. 시간 축은 이벤트 간 균등 + 바뀐 시리즈 수 가중(최대 +60%)으로 전체 20~40초(= 이벤트 수 × 0.8초를 20~40에 가둠)다.
- 화면은 `ui/replay.html` + `ui/app/replay/`(`KBO.Replay.open(trace, {host, embedded})`, 외부 라이브러리 없음): 왼쪽 9×5 슬롯 격자 위에 시리즈 카드를 transform으로 놓고 320ms 전환으로 움직인다. 오른쪽은 소프트 5단계(미배정·이동 횟수 편차·거리 편차·휴일 편차·총 이동거리 km) 계단 곡선과 현재 시점 커서, 아래는 해설 한 줄과 재생/일시정지·0.5×/1×/2×·한 스텝 앞뒤·슬라이더·처음으로다. `replay.html?src=<json>&t=<초>&autoplay=0`로 열고, 기본은 `ui/core/trace-sample.json`(data/baseball의 복사본)이다.
- 위저드 연동: `app.js`가 SSE `done`의 `trace`를 `run.trace`에 두고, ② 검토·실행의 「지난 실행 결과」가 `S.lastRun.trace`가 있을 때만(서버 엔진) 「탐색 과정 보기」 버튼을 보여 모달(`modal=replay`)로 같은 재생기를 띄운다. 트레이스 없이 주소로 열면 샘플을 읽는다. 지난 실행은 메모리에만 있어 새로고침하면 버튼이 사라진다.
- 점검: Node 21/21, 자가 점검 64/64(1440·1920, 재생기 5개 추가), 화면 점검 35경로×2크기 70/70(`x-replay` 추가). 점검 스크립트는 file://에서 샘플 JSON을 읽도록 `--allow-file-access-from-files`를 켰다. 스크린샷 `ui/shots/replay-play-1440.png`·`replay-mobile-375.png`·`s5-replay-*.png`.
- 빈틈: 모바일(≤700px)은 3열 격자에 페이지 세로 스크롤을 허용했고 헤드리스 최소 폭(500px) 탓에 375px 화면은 직접 확인하지 못했다. KEEP 모드로 Hard 위반이 남은 트레이스는 미배정 카드를 숨기고 머리글에 수만 적는다. 무브 종류 이름(§7-2)은 아직 없다.

## 5. 아키텍처
- **서버**: 기존 Maven 프로젝트에 `org.optaplanner.examples.baseball.web` 패키지. JDK 내장 `HttpServer`, 정적 파일(`ui/` + 소개 페이지) 서빙, 작업 큐(동시 실행 1~2개, 대기 순번 표시), 결과 캐시(파라미터 해시+시드 → 결과 JSON).
- **REST**: 기준 요구사항 §7.3을 따르되 응답에 `trace`와 `seedResults`를 더한다. `POST /api/v1/solve` → `{jobId}`, `GET /api/v1/solve/{jobId}/events`(SSE: `seed-best`, `best`, `done`), `POST /api/v1/score`(실제 일정 채점).
- **UI**: `ui/core/engine-adapter.js`의 REST 어댑터를 구현해 Mock과 바꿔 끼운다. 트레이스 재생기와 보여주는 문은 새 페이지.
- **운영**: VM 1대, systemd, Java 25, Cloudflare 프록시(HTTPS·캐시·방어), IP당 동시 1작업, 애널리틱스, 피드백 폼.

### 5.1 서버 실행과 API (2026-10-20 구현, `src/main/java/org/optaplanner/examples/baseball/web/`)

```bash
scripts/run-server.sh --port 8080 --ui ui --max-seconds 30 --seeds 8
```

| 파일 | 역할 |
| :--- | :--- |
| `BaseballWebServer` | JDK 내장 HttpServer. `ui/` 정적 서빙, REST·SSE 라우팅, CORS, 본문 크기 제한 |
| `JobManager` | 작업 큐(동시 1개), 결과 캐시(문제+옵션 SHA-256 → 결과, LRU 200), IP당 동시 1작업(429) |
| `MultiStartSolver` | 시드 N개를 단일스레드 솔버로 병렬 실행, 최고 해 선택, 시드별·전체 best 이벤트, 트레이스(`bench.SolveTrace`) |
| `ProblemCodec` | UI 프로젝트 JSON ↔ `BaseballSolution`. 시리즈 id = matches 위치, 슬롯 id = calendar 위치 |
| `SolveOptions`·`ServerLimits` | 옵션 한도: 실행 시간 1~30초(기본 10), 시드 1~코어 수(기본 min(8, 코어)) |

| API | 설명 |
| :--- | :--- |
| `GET /api/v1/info` | 이름·한도·큐 길이. UI는 이걸로 서버를 감지해 REST 엔진으로 전환한다 |
| `POST /api/v1/solve` `{problem, options, mode}` | `{jobId, status}`. options: timeLimitSec, unimprovedSec, seed, seeds, init(KEEP·SCRATCH) |
| `GET /api/v1/solve/{jobId}/events` | SSE: `queued`(대기 순번) → `status` → `seed-best`·`best` → `done`(plan, score, seedResults, trace) / `error` |
| `GET /api/v1/solve/{jobId}` · `POST .../stop` | 상태 조회, 조기 종료 |
| `POST /api/v1/score` `{problem, plan?}` | 같은 채점기로 임의 plan 채점(실제 일정 채점용) |

UI 연결: `ui/core/engine-adapter.js`의 REST 어댑터(큐·시드 이벤트 수신, 점수 응답에 브라우저 위반 목록 병합), `ui/app/common/app.js`가 http(s)로 열리면 `/api/v1/info`를 탐색해 자동으로 REST를 고른다. `ui/app/studio/step-review.js`의 "편성 시작"은 목업에서 실제 `app().solve()` 호출로 바뀌었다(서버 없으면 브라우저 Mock 엔진).

실행 옵션(2026-10-20 정리): UI 실행 시간 프리셋은 서버 기준 10·20·30초(기본 10초, 개선 없음 종료는 절반), 예전 1·5·30분 값은 열 때 자동 이전. 지금 일정에 Hard 위반이 있으면 「다듬기(KEEP)」 대신 「처음부터 새로 짜기(SCRATCH)」로 실행한다(화면에 안내). 사전 점검에 공유 구장 용량(잠실 홈 k연전 ≤ k연전 슬롯) 차단 항목을 더했다. 시연용 가상 위반은 홈·원정 뒤집기 대신 슬롯 맞바꾸기로 만들어 구조적으로 편성 가능하게 했다.

알려진 제약: SCRATCH에서는 사용자 핀이 초기해 생성기의 개막전·어린이날 핀으로 덮인다. 초기해 생성기는 잠실 홈 3연전 수가 3연전 슬롯 수와 정확히 같아야 한다(적어도 구조가 다르면 거부).
