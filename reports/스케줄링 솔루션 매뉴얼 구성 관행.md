# 업무 순서로 짜고, 판단은 사람에게 맡기는 매뉴얼

**우리 PDF 매뉴얼의 표준 구성은 「앞부분(표지·적용 버전·바뀐 점·읽는 법) → 편성 스튜디오가 하는 일과 담당자가 정하는 일(개념) → 처음 한 번 따라 하기(실습) → 업무 순서대로 네 장(편성 조건 입력·검증 → 운영 방침·실행 → 현재 결과 분석 → 실행 결과 비교·확정) → 이럴 때는(목적별 안내) → 문제 해결 → 규칙·기준 목록과 용어 풀이(참조) → 자주 묻는 질문 → 도움 받는 곳」이고, 소개 자료는 「일정이 왜 어려운가 → 원리 한 문단 → 이익별 묶음 → 네 단계 흐름 → 결정은 담당자가 한다 → 결과 숫자 → 믿을 수 있는 이유 → 문의」 순서입니다.** 이 순서는 네 갈래 근거가 겹치는 지점입니다. ISO/IEC/IEEE 26514는 내용을 정보 유형(개념·절차·참조·문제 해결·용어집)으로 나누고 Diátaxis는 실습·방법 안내·참조·설명을 섞지 말라고 하며, 최적화 제품 Timefold의 문서는 「소개 → 시작하기 → 개념·용어 → 규칙 → 결과 읽기 → 비교 → 변화 대응 → FAQ」, 아마추어용 편성 도구 도움말은 「시작하기 → 조건 → 편성 → 수정 → 공유 → 문제 해결」 순서이고, 소개 자료의 이야기 순서는 Fastbreak의 4단계와 NFL·Premier League의 설명 글에서 왔습니다. 변화 관리 연구는 사람이 알고리즘의 실수를 한 번 보면 신뢰를 빨리 거두지만 결과를 고칠 수 있으면 훨씬 기꺼이 쓴다고 보여 주므로, 매뉴얼은 처음부터 「자동 편성은 안을 내고, 담당자가 순서를 정하고, 비교해 고르고, 확정한다」는 구도로 써야 합니다. 관행에서 크게 벗어나는 곳은 하나입니다. 변화 관리 관행(ADKAR)은 첫머리에 「왜 바꾸나·무엇이 달라지나」를 두지만, 우리 매뉴얼은 사용자의 지금 업무 방식을 언급하지 않으므로 이 부분을 중립적인 역할 분담 장으로 바꾸고 「왜」의 메시지는 KBO 쪽 책임자의 몫으로 남깁니다. 근거의 한계도 분명합니다. 프로 리그용 편성 제품의 공개 사용자 매뉴얼이나 브로슈어 목차는 찾지 못했으므로, 이 구성안은 업무 사용자용 최적화 제품 문서, 아마추어용 편성 도구 도움말, 문서 표준을 겹쳐 맞춘 결과입니다.

## 소개 자료는 "문제의 크기 → 원리 → 이익 → 4단계 → 사람의 선택" 순서로 쓴다

**프로 리그용 편성 제품의 공개 소개 자료는 짧은 마케팅 페이지가 전부이고, 뼈대는 4단계 흐름입니다.**

Fastbreak Pro 기능 페이지의 "How It Works" 4단계는 다음과 같습니다([Fastbreak Pro Features](https://www.fastbreak.ai/pro/features)).

| 단계 | 하는 일 |
| :--- | :--- |
| 1. Define Goals & Constraints | 목표·팀·날짜를 정하고, 규칙을 우선순위대로 매긴다 |
| 2. Optimize & Review | 일정을 만들고 여러 버전을 비교한다. 이동 과다·불균등 휴식 같은 문제를 표시해 준다 |
| 3. Collaborate & Adjust | 초안을 구단·구장·방송사와 공유하고 끌어다 놓아 고친다 |
| 4. Finalize & Publish | 승인된 일정을 잠그고 공개한다 |

이 순서는 우리 스튜디오의 흐름(조건 → 운영 방침·실행 → 분석 → 비교·확정)과 거의 그대로 겹칩니다.

같은 회사의 Smarter Scheduling 페이지는 다음 순서로 씁니다([Fastbreak Smarter Scheduling](https://www.fastbreak.ai/pro/smarter-scheduling)).

1. 좋은 일정이 왜 중요한가
2. 원리 한 덩어리
3. 이익을 하나씩: 공정성 → 중계 가치 → 피로 감소 → 관중 수입 → 구장 조정
4. 데모 요청

첫 화면은 고객 리그 로고·추천사, 수상, 뉴스, 문의 블록으로 이어지고, FAQ 대신 "Questions?" 문의 블록을 둡니다([Fastbreak](https://www.fastbreak.ai/)).

**업계의 공통 설명 방식은 "후보를 여러 개 만들고, 사람이 고르고, 확정한다"입니다.**

- **NFL**: AWS 블로그에 따르면 밤마다 수천 개 시나리오를 돌려 수십 개 후보를 얻고, 사람의 "art"와 분석의 "science"가 함께 검토합니다([AWS 블로그](https://aws.amazon.com/blogs/media/a-look-inside-the-making-of-an-nfl-football-schedule)).
- **칠레 프로축구(ANFP) 논문**: 조건을 먼저 정해 모두에게 알리고, 모델이 몇 개의 해를 내면 ANFP가 최종판을 고른다고 씁니다. 이 과정이 구단과의 합의를 돕는다고 하고, 고위 관계자가 여러 해 만에 처음으로 구단 불만이 거의 없었다고 말했다고 적습니다([Durán 외 PDF](https://www.dii.uchile.cl/~gduran/docs/papers/OR_Chilean_soccer.pdf)).
- **Premier League 2026/27 설명 글**: 질문형 머리말 7개로 구성됩니다. 시즌 길이 → 작업 순서 → 작업 시작 시점 → 배정 방법 → 기본 규칙 → 그 밖의 고려 사항 → 공개 전 검토 순서입니다([premierleague.com](https://www.premierleague.com/en/news/4324541)).
- **성공 기준의 말투**: Fast Company 기사는 "If everyone hates you equally, you've done your job right"라는 말을 전합니다([Fast Company/Yahoo](https://finance.yahoo.com/news/fastbreak-ai-solving-complex-riddle-100000953.html)). 성공을 "모두에게 고르게"라는 공정성의 말로 표현합니다.

**경우의 수의 크기를 숫자로 먼저 보여 주는 것도 공통입니다.** AWS의 NFL 소개 페이지는 다음 숫자를 앞에 내세웁니다([AWS NFL](https://aws.amazon.com/sports/nfl/schedule)).

- 가능한 일정 1,000조(quadrillion) 개
- 272경기, 576개 경기 시간대, 방송사 7곳

다만 같은 회사 자료 사이에서 숫자가 어긋납니다. 소개 페이지는 고려 요소를 "26,000+"로, 블로그는 규칙을 "20,000+"로 적고, 소개 페이지 안에서도 분석한 일정 수를 "over 100,000"과 "millions"로 다르게 씁니다. 숫자를 쓸 때는 한 원천에서 일관되게 가져와야 한다는 반면교사입니다.

**최적화 제품 쪽에서는 독립된 브로슈어 목차를 찾지 못했습니다.** 대신 Timefold는 소개 페이지 한 장을 독자별 절로 나눕니다([Timefold Employee Shift Scheduling](https://docs.timefold.ai/employee-shift-scheduling/latest/introduction)).

1. 연동 개발자용
2. 아키텍트용
3. 제품·업무·의사결정자용

설명회에서 PDF 한 부를 경영진과 담당자가 함께 볼 우리 상황에서는, 소개 자료 첫머리에 "의사결정자에게는 이 쪽"을 따로 두는 방식이 참고가 됩니다.

## 사용자 매뉴얼은 "시작하기 → 조건 → 실행 → 결과 읽기 → 비교 → 문제 해결"로 짠다

### 아마추어용 편성 도구는 할 일 순서로 짧은 글을 묶는다

**도움말 센터는 하는 일 순서로 묶고, 글 하나에 한 가지 일을 다룹니다.**

Diamond Scheduler 현행 지식 베이스의 큰 분류 순서는 다음과 같습니다([Cactusware 지식 베이스](https://support.cactusware.com/constraints/time-and-date-constraints)).

1. 대시보드 둘러보기
2. 리그 마법사
3. 편성
4. 달력·시간대
5. 조건
6. 관리 포털·공개 페이지
7. 팀·구장
8. 계정·요금

구판은 탭(화면)별 설명과 "Common Problems"(시간대가 없다고 나올 때, 편성이 끝나지 않을 때)를 따로 두었습니다([Cactusware 구판](https://legacy.cactusware.com/knowledge-base/league-creation-assistant/)). 현행판은 할 일 중심입니다. 업계가 화면 순서에서 업무 순서로 옮겨 갔다고 읽을 수 있습니다.

**대표 글의 구성은 다음과 같습니다.**

| 글 | 구성 | 분량·그림 |
| :--- | :--- | :--- |
| LeagueLobster "Getting Started with LITE" ([LeagueLobster](https://help.leaguelobster.com/en/articles/437288-getting-started-with-lite)) | 영상 → 1단계 설정 → 2단계 일정 수정 → 3단계 공유 → 4단계 점수·순위 → 추천 읽을거리 | 약 1,200단어, 그림 6개 |
| Diamond "Scheduling Overview" ([Cactusware](https://support.cactusware.com/scheduling/scheduling-overview)) | 6단계(만들기·설정 → 요약 확인 → 시간대 → 편성 → 결과 확인·다시 편성·개별 수정) | 약 250~300단어, 단계마다 화면 하나 |

도움말 글은 대개 200~2,000단어로 짧습니다. 맨 앞에 영상을 두고, 단계마다 화면을 하나씩 붙입니다.

**한계를 따로 밝히는 글도 있습니다.** LeagueLobster는 "Limitations" 글을 둡니다. 예를 들어 하루 최대 경기 수는 정할 수 있지만 최소 경기 수는 정할 수 없다고 적습니다([LeagueLobster Limitations](https://intercom.help/leaguelobster/en/articles/5057127-limitations), 검색 요약만).

**용어집과 FAQ는 드뭅니다.** 이번에 본 아마추어용 도구 자료에서는 용어집과 FAQ가 거의 보이지 않았습니다. 대신 각 글 안에서 친숙한 말로 바꿔 씁니다. 예를 들어 "NoPlay All Day"를 "Blackout date"라고 풀어 씁니다([Cactusware](https://support.cactusware.com/constraints/time-and-date-constraints)).

### 최적화 제품 문서는 개념·용어를 앞에, 결과 읽기와 비교를 뒤에 둔다

**공개 근거가 가장 충실한 Timefold 문서의 순서는 다음과 같습니다**([Timefold Employee Shift Scheduling](https://docs.timefold.ai/employee-shift-scheduling/latest/introduction)).

1. 소개
2. 가장 작은 예제 한 번 돌리기(Hello world)
3. 단계별 레슨 7개
4. 사용자 안내
   - 용어 → 사용 사례 → 규칙 → 입력 점검 → 출력과 지표 → 점수 분석 → 시각화 → 배정 못 한 항목 분석
5. 기능별 안내: 규칙 묶음 하나가 한 장(근무 계약, 가용성, 공정성 등)
6. 변화 대응: 수동 개입, 추천, 실시간 재편성
7. 기타: FAQ, 변경 이력, 업그레이드, 기능 요청

**업무 목적별 안내를 따로 둡니다.** 플랫폼 문서에는 기능 설명과 별도로 "업무 목적별 안내(job-oriented guides)"가 있습니다([Timefold Platform](https://docs.timefold.ai/timefold-platform/latest/introduction)).

- "Balancing different optimization goals"(서로 다른 목표 사이의 균형 잡기)
- "Validating an optimized plan with Explainable AI"(최적화된 계획을 설명 가능한 AI로 검증하기)

**글 하나는 짧게 씁니다.** 인력 스케줄링 제품 Quinyx의 도움말 글은 "Key highlights → How to use it → Why this matters" 세 덩어리로 짧게 끝납니다([Quinyx](https://quinyx.helpdocs.io/l/en/article/23q5v84x00-auto-assign-rule-configuration)).

### 문서 표준은 같은 구성을 "정보 유형"으로 정리해 준다

**ISO/IEC/IEEE 26514:2022는 정보의 구조를 유형별로 나눕니다.** 2021년 초안(DIS) 목차 기준으로는 다음 유형을 따로 다룹니다([26514 DIS 샘플](https://cdn.standards.iteh.ai/samples/77451/1a554e3e44ba4735afd336ccfe48e9e5/ISO-IEC-IEEE-DIS-26514.pdf)).

- 개념 정보
- 절차 정보
- 참조 정보
- 문제 해결 정보
- 오류 메시지
- 용어집
- FAQ
- 인쇄용 정보

형식 쪽으로는 목차·색인·검색, 위험·경고·주의 표시, 그림 형식, 버전 관리를 다룹니다. 이 표준은 사용자가 인쇄하도록 전자 형태로 내는 정보, 곧 PDF 매뉴얼도 "인쇄용 정보"로 정의합니다.

**2008판의 구성 요소는 한 권짜리 PDF의 점검표로 여전히 쓸모 있습니다**([26514:2008 샘플](https://cdn.standards.iteh.ai/samples/43073/d8447563ac1e481897744ba18955894d/ISO-IEC-26514-2008.pdf)).

- 식별 정보
- 문서 사용법 안내
- 운영 개념
- 절차와 튜토리얼
- 입력 항목 설명
- 오류 메시지와 문제 해결
- 경고와 주의
- 용어
- 관련 정보원
- 목차·그림 목록·색인

**표준이 정한 단계의 뜻도 쓰는 방식을 정해 줍니다.** 표준은 단계를 사용자가 할 행동으로 정의하고 "소프트웨어의 반응은 단계가 아니다"라고 밝힙니다. 그래서 "잠시 뒤 진행 막대가 나타납니다" 같은 결과 문장은 번호를 따로 매기지 않고 해당 단계 끝에 붙입니다.

**Diátaxis는 네 유형을 섞지 말라고 합니다**([Diátaxis](https://diataxis.fr/start-here/)).

- **튜토리얼**: 실습으로 익히기
- **방법 안내**: 실제 업무 목표를 돕기
- **참조**: 중립적인 사실
- **설명**: "왜"에 답하기

경계를 흐리는 것이 많은 문서 문제의 근원이라고 봅니다. 한 권짜리 PDF에서는 장 단위로 유형을 나눠 담으면 이 원칙을 지킬 수 있습니다.

**한국 공공·SI 매뉴얼의 관행은 다음 순서입니다.**

> 표지 → 제·개정 이력 표(버전·일자·구분·내용·작성자) → 목차 → 개요(매뉴얼 구성·용어) → 메뉴 구성 → 화면별 설명 → 문제 해결

예로 서울시 사용자 매뉴얼([서울시 PDF](https://news.seoul.go.kr/economy/files/2015/07/55b97e96085251.67161727.pdf))과 한성대 관리자 매뉴얼([한성대 PDF](https://hansung.ac.kr/sites/homepage/contents/homepage/%EA%B4%80%EB%A6%AC%EC%9E%90%EB%A7%A4%EB%89%B4%EC%96%BC.pdf))이 있습니다. 둘 다 검색 요약으로만 확인했습니다. 목차를 정한 단일 국가 표준(TTA 등)은 확인되지 않았습니다.

**문장 기준은 국립국어원 『쉬운 공문서 쓰기 길잡이』(2022)를 따를 수 있습니다.** 짧게 끊고, 어려운 말은 순화어로 바꾸라는 원칙입니다([공공데이터포털](https://www.data.go.kr/data/15118448/fileData.do)).

### 쓰는 방식은 세 스타일 가이드가 같은 말을 한다

- **절차**: 번호 단계로 쓰고, 한 단계에 한 행동, 명령형으로 씁니다. 행동보다 위치를 먼저 말하고, 화면 요소 이름은 굵게 적습니다. 절차 하나는 한 화면에 들어가게 씁니다([Microsoft 절차 작성](https://learn.microsoft.com/en-us/style-guide/procedures-instructions/writing-step-by-step-instructions)).
- **화면 캡처**: 말로 설명하기 어려울 때만 넣습니다. 필요한 부분만 잘라서 넣고, 같은 내용을 글로도 씁니다. 화면이 바뀌면 다시 캡처하고, 그림은 번호로 가리킵니다([Google Images](https://developers.google.com/style/images)).
- **알림 상자**: 참고·주의·경고로 나누고 아껴 씁니다. 작업에 꼭 필요한 내용은 알림 상자가 아니라 해당 단계 앞 본문에 둡니다([Google Notices](https://developers.google.com/style/notices)).
- **분량**: 표준 수치는 없습니다. 26514의 "최소주의"(꼭 필요한 것과 완전성에 필요한 최소)가 기준입니다.

## 최적화 제품의 문서는 "규칙 → 순서 → 결과 근거 → 비교 → 확정"을 따로 설명한다

### 규칙과 순서: 일상어로, 숫자가 든 짧은 문장으로

**규칙은 "꼭 지키는 것"과 "되도록 지키는 것", 그리고 그 사이의 중요도로 설명합니다.**

Timefold는 세 층으로 나눕니다([Timefold 목표 균형](https://docs.timefold.ai/timefold-platform/latest/guides/balancing-different-optimization-goals)).

1. 언제나 지키는 규칙
2. 자원이 모자라도 최대한 배정하는 것
3. 최적화 목표

여기에 "하나의 최고 일정은 없고 업무 우선순위에 따른 맞바꿈만 있다"는 관점을 분명히 적습니다.

**조정의 효과를 장담하지 않는다는 점도 밝힙니다.** 같은 글은 가중치를 두 배로 올려도 관련 지표가 절반이 되지 않으며 효과는 예측하기 어렵다고 경고합니다. 그리고 다음 반복을 권합니다.

> 가장 모자란 지표를 고른다 → 그 지표를 움직이는 규칙을 찾는다 → 조정한다 → 다시 돌린다 → 비교한다 → 다음 우선순위로 넘어간다

**업무 사용자용 제품은 숫자 대신 등급을 보여 주기도 합니다.**

- **Quinyx**: 우선순위를 Mandatory/High/Medium/Low 등급으로 고르게 합니다([Quinyx](https://quinyx.helpdocs.io/l/en/article/23q5v84x00-auto-assign-rule-configuration)). 등급이 실제로 어떻게 작동하는지는 공개 문서에 설명이 없습니다.
- **Fastbreak**: 공개 페이지에서 규칙을 "ranked by priority"로 정한다고만 쓰고, 내부 원리는 밝히지 않습니다([Fastbreak Pro Features](https://www.fastbreak.ai/pro/features)).

**우리 제품에 옮기면 이렇게 쓸 수 있습니다.** 우리 운영 방침의 "우선순위 순서"는 등급식에 가깝습니다. 매뉴얼에는 비교 원칙 한 문단만 일상어로 쓰고, 내부 점수 구조는 넣지 않습니다. 그 원칙은 스튜디오의 「운영 방침 설명하기」 창이 이미 이렇게 씁니다. "1순위가 허용 수준 안에 들어오면 만족으로 보고, 그때부터 2순위로 결과를 가립니다. 1순위를 넘은 두 결과는 2순위가 아무리 좋아도 1순위를 덜 넘은 쪽을 고릅니다." 매뉴얼은 이 문장을 그대로 쓰면 됩니다(`ui/app/studio/objective-help.js`에서 확인).

**스포츠 쪽은 규칙을 숫자가 든 짧은 문장으로 씁니다.**

- **Premier League**: "연속 5경기 중 홈/원정 3:2"처럼 문장으로 풉니다([premierleague.com](https://www.premierleague.com/en/news/4324541)).
- **칠레 리그**: 조건 25개를 번호 매긴 평이한 문장으로 쓰고, 조건마다 이유(공정성, 수입, 경찰 배치)를 붙입니다([Durán 외 PDF](https://www.dii.uchile.cl/~gduran/docs/papers/OR_Chilean_soccer.pdf)).
- **Diamond Scheduler**: 조건 종류마다 한 줄 정의, 친숙한 말 바꾸기, 쓰임새 예를 붙입니다([Cactusware](https://support.cactusware.com/constraints/time-and-date-constraints)).
- **용어**: 비개발자용 공개 자료는 "hard/soft"를 쓰지 않았습니다.

우리 규칙도 같은 형식으로 쓸 수 있습니다. 예를 들면 "연속 경기일은 최대 6일, 더블헤더는 최대 2번"입니다.

### "왜 이 결과인가": 업무 지표부터, 막연한 점수 말고

**설명은 다섯 층으로 쌓습니다.** Timefold의 "설명 가능한 AI로 계획 검증하기" 글은 다음 순서입니다([Timefold 설명 가능성](https://docs.timefold.ai/timefold-platform/latest/guides/validating-an-optimized-plan-with-explainable-ai)).

1. 실제 업무 지표
2. 규칙별 점수 분석
3. 구체적인 근거 예시
4. 배정하지 못한 항목과 그 이유
5. 시각화로 눈으로 확인

목표는 "왜 X를 하지 않았나"라는 질문을 이해할 수 있는 답으로 바꾸는 것입니다. 실제로 쓰기 전에는 표본을 직접 확인하고, 움직이면 안 되는 배정은 고정하며, 일부(한 팀)에서 시작해 신뢰가 쌓이면 넓히라고 권합니다.

**결과를 믿기 전에 할 일도 정해 둡니다.** 결과 읽기 안내는 결과를 믿기 전에 상태·검증 오류·경고부터 보라고 하고, 지표 하나만 보지 말고 함께 읽으라고 합니다([Timefold 결과 해석](https://docs.timefold.ai/timefold-platform/latest/how-tos/interpreting-model-run-results)).

**못 넣은 경기는 두 상태로 나눠 설명합니다.** 현장용 도구 LeagueLobster의 방식입니다([LeagueLobster Constraints](https://help.leaguelobster.com/en/articles/805124-constraints)).

| 상태 | 뜻 |
| :--- | :--- |
| 들어갈 시간대가 아예 없음 | 조건이 모든 시간대를 막은 경우 |
| 아직 배정 안 됨 | 시간대는 있지만 이미 찬 경우 |

상태마다 대처법(경기 옮기기, 조건 고치기, 다시 배정)을 붙입니다. 곧 추가될 시즌 중 재편성의 "못 넣은 경기 표시"에 그대로 맞는 형식입니다.

### 비교와 확정: 엔진 문서에는 없고, 계획 플랫폼에 있다

**비교 관행은 "같은 조건을 여러 설정으로 돌린 결과를 나란히 놓고, 차이만 따로 보는 것"입니다.**

- **Timefold**: 실험(Experiments)과 비교 화면에서 지표·점수·규칙 내역을 나란히 놓고, 차이를 백분율로 보여 줍니다([Timefold Changelog](https://docs.timefold.ai/timefold-platform/latest/changelog)).
- **IBM Decision Optimization**: 두 시나리오를 나란히 보고 "차이만 보기"로 바꿀 수 있습니다([IBM 시나리오 비교](https://www.ibm.com/docs/en/cloud-paks/cp-data/5.4.x?topic=scenarios-comparing), 검색 요약만).
- **비교할 때 볼 것**: 목표 지표가 좋아졌는지, 그리고 다른 중요한 지표가 크게 나빠지지 않았는지를 함께 봅니다([Timefold 목표 균형](https://docs.timefold.ai/timefold-platform/latest/guides/balancing-different-optimization-goals)).

**확정 단계는 엔진 문서에 거의 없고, 계획 플랫폼에 나타납니다.**

- **ServiceNow**: 시나리오를 비교한 뒤 하나를 승인하면 그것이 실제 계획이 된다고 안내합니다([ServiceNow](https://www.servicenow.com/docs/r/MrftC6mNgCta3UqwXSW7Kg/9Tw6Je36J5v82Kpi66A~7A), 검색 요약만).
- **Kinaxis**: 사용자 후기에 바꿔 본 시나리오를 "버리거나 확정한다"는 흐름이 나옵니다([Gartner Peer Insights](https://www.gartner.com/reviews/market/supply-chain-planning-solutions/vendor/kinaxis/product/kinaxis-maestro-platform/likes-dislikes)).

우리 스튜디오의 순위표 + 두 버전 비교 + 「여기서 갈림」 + 확정 + 엑셀 내보내기는 이번에 본 공개 자료보다 자세합니다. 매뉴얼에서 독립된 장을 둘 만합니다.

## 변화 관리 관행은 "매뉴얼은 지식과 실행만, 나머지는 다른 자료로"를 가리킨다

### ADKAR: 단계마다 맡는 자료와 전하는 사람이 다르다

**ADKAR는 변화의 다섯 단계를 나누고, 단계마다 전하는 사람과 자료를 다르게 봅니다**([Prosci ADKAR](https://www.prosci.com/blog/adkar-core-to-the-people-side-of-change)).

| 단계 | 내용 | 전하는 사람·자료 |
| :--- | :--- | :--- |
| Awareness(왜 바꾸나) | Awareness가 부족한 것이 저항의 가장 큰 원인 | 경영진이 사업상 이유를 설명 |
| Desire(내게 무엇이 좋은가) | 개인이 스스로 정하는 단계 | 직속 관리자가 답함 |
| Knowledge | 교육으로 첫 지식을 줌 | 교육, 연습, 현장 코칭, 작업 보조물(job aid) |
| Ability | 실제로 해 보일 수 있는 상태. 이때 사업 성과가 생김 | 연습 시간, 장애물 제거 |
| Reinforcement | 변화를 유지 | 인정, 측정, 지속 지원 |

Prosci 연구에 따르면 직원들은 사업상 이유는 경영진에게서, 개인에게 미치는 영향은 직속 관리자에게서 듣기를 원합니다. 프로젝트 팀에게서 듣는 것은 선호하지 않습니다([Prosci 커뮤니케이션 점검표](https://prosci.com/blog/communications-checklist-for-change-management)).

**따라서 매뉴얼 한 권이 다섯 단계를 다 떠안지 않습니다.** 본문은 Knowledge와 Ability, 곧 따라 하기와 연습에 집중합니다. "왜 바꾸나"는 조직의 책임자 목소리로 따로 냅니다.

**이 원칙이 우리 제약과 정확히 맞물립니다.** 우리 매뉴얼은 사용자의 지금 업무 방식을 언급하지 않습니다. 그러므로 ADKAR식 "무엇이 달라지나" 머리말을 시스템을 만든 쪽의 목소리로 쓰지 않습니다. 대신 "이 시스템이 하는 일과 담당자가 정하는 일"이라는 중립적인 개념 장을 둡니다.

### 도입 자료는 긴 안내서와 짧은 작업 보조물로 층을 나눈다

**업계의 도입 키트는 다섯 층으로 나뉩니다.**

1. 긴 안내서
2. 짧은 작업 보조물(빠른 참고 카드·요약 카드·점검표)
3. 알림 자료(메일·포스터·FAQ)
4. 연습 환경
5. 질문 창구와 동료 도우미

예로 Microsoft Teams 변화 관리 전략([Microsoft Learn](https://learn.microsoft.com/en-us/MicrosoftTeams/change-management-strategy))과 Workday를 도입한 볼티모어시 자료([Baltimore City Workday](https://workday.baltimorecity.gov/node/19162))가 있습니다.

**작업 보조물(job aid)은 이미 교육받은 사람이 일하는 도중에 펴 보는 자료입니다.** 교육 자료는 기초 지식을 쌓는 자료라서 둘을 구분합니다([ScreenSteps](https://blog.screensteps.com/job-aids-vs-training-guides), 벤더 블로그).

**긴 매뉴얼 한 권이 세 역할을 겸할 수 있습니다.** 교육 전에는 소개, 교육 중에는 교재, 교육 뒤에는 참고서 역할입니다([Wikipedia Training manual](https://en.wikipedia.org/wiki/Training_manual)). 혼자 읽기와 설명회를 겸하는 우리 PDF가 이 형태입니다.

**처음에는 업무 시나리오를 좁힙니다.** Microsoft는 첫 시범의 업무 시나리오를 3개 이하로 고르라고 권합니다([Microsoft Learn](https://learn.microsoft.com/en-us/MicrosoftTeams/change-management-strategy)). 매뉴얼의 "처음 한 번 따라 하기"와 "이럴 때는" 장의 범위를 좁히는 근거가 됩니다.

**교육 시점도 정해 둡니다.** 출시보다 너무 일찍 교육하면 잊고, 너무 늦게 하면 연습할 시간이 모자랍니다([Prosci Knowledge 전자책 재게시본](https://www.scribd.com/document/399024164/4-ADKAR-Knowledge-eBook-pdf)). 편성이 1년에 몇 번뿐인 업무라면, 시즌 직전 복습용 요약 카드가 따로 있어야 합니다.

### 알고리즘 신뢰: 고칠 수 있다는 사실이 수용을 만든다

**사람은 알고리즘이 틀리는 것을 한 번 보면 신뢰를 빨리 거둡니다.** Dietvorst 외(2015)는 이 경향을 5개 실험으로 보였습니다. 알고리즘이 더 정확하다는 것을 직접 본 뒤에도 같은 경향이 나타났습니다([Penn](https://repository.upenn.edu/fnce_papers/58)).

**결과를 고칠 수 있으면 사람은 훨씬 기꺼이 씁니다.** 후속 연구(2018)에서는 불완전한 알고리즘이라도 결과를 조금 고칠 수 있게 하자 훨씬 많이 썼고 성과도 좋아졌습니다. 수정 폭을 크게 제한해도 효과가 유지됐습니다([Wharton PDF](https://marketing.wharton.upenn.edu/wp-content/uploads/2020/07/Dietvorst-Overcoming-Algorithm-Aversion.pdf)).

**계획 담당자의 불신은 현장에서도 확인됩니다.**

- **TU Eindhoven 연구 과제**: 계획 담당자가 계획 도구를 믿지 못하고 조언에서 자주 벗어나는 문제에서 출발했습니다([TU/e](https://research.tue.nl/en/projects/improving-the-use-of-decision-support-systems/)).
- **Augsburg 대학 연구**: 기술 지식이 깊지 않은 이해관계자일수록 최적화 결과에 대한 설명을 강하게 원했습니다([Uni Augsburg](https://opus.bibliothek.uni-augsburg.de/opus4/frontdoor/deliver/index/docId/128225/file/128225.pdf)).

**대응책은 네 가지로 모입니다.**

1. 규칙 위반을 설명한다
2. 두 안을 비교한다
3. 일부를 고정하고 다시 짠다
4. 최종 결정은 사람이 한다

엔진 벤더 Timefold의 블로그도 같은 방향입니다([Timefold 블로그](https://timefold.ai/blog/explainable-ai-how-to-build-trust-in-optimization)). "알고리즘이 그렇게 했다"는 답뿐이면 담당자가 계획을 믿지 않는다고 하고, 목표를 "맹목적 신뢰"가 아닌 "근거 있는 확신"으로 둡니다.

**매뉴얼에 주는 함의는 세 가지입니다.**

- 도구의 한계를 미리 솔직하게 씁니다.
- 담당자가 고치고 고르는 기능을 앞세웁니다.
- 결과 설명은 담당자의 말(연전, 이동 거리, 월요일 경기)로 씁니다.

### 구성안 전체에 적용하는 형식 규칙

이 규칙들은 26514, 세 스타일 가이드, PDF 접근성 관행을 합친 것입니다.

- **장 첫머리**: "이 장에서 할 수 있는 일"을 한 줄로 씁니다.
- **절차**: 한 단계에 한 행동을 쓰고, 위치를 먼저 말합니다. 예: "**운영 방침** 화면에서 **실행**을 누릅니다." 화면의 반응은 같은 단계 끝에 붙입니다.
- **화면 캡처**: 절차 하나에 많아야 한 장입니다. 필요한 부분만 잘라 번호를 붙이고, 같은 내용을 글로도 씁니다.
- **알림 상자**: 참고와 주의 두 가지를 주로 씁니다. 경고는 되돌릴 수 없는 일(예: 확정)에만 씁니다.
- **PDF 설정**: 제목 계층을 실제 제목 스타일로 만들어 책갈피·목차·태그가 함께 생기게 하고, 문서 언어를 한국어로 지정합니다([pdf-tools PDF/UA](https://www.pdf-tools.com/pdf-ua-standard-explained)).
- **쓰지 않는 말**: hard/soft, 시드, 데이터셋 같은 말은 본문 어디에도 쓰지 않습니다. 화면 글 규칙과 같고, 알고리즘 수용 연구의 "인지적 적합성"(익숙한 말로 설명할 것)과도 맞습니다([Burton 외](https://research.cbs.dk/en/publications/a-systematic-review-of-algorithm-aversion-in-augmented-decision-m/)).
- **화면 말과 맞추기**: 규칙은 화면처럼 "반드시 지키는 규칙"으로 씁니다. 화면의 상태 표시는 "자동 편성", 설명 창은 "엔진"을 함께 쓰므로 매뉴얼은 "자동 편성" 하나로 통일합니다(화면 쪽은 맨 끝 「정할 것」 6번).
- **색인**: 26514 형식 절에는 있지만, 쪽수가 적으면 PDF 검색으로 대신할 수 있습니다.

### 매뉴얼에 넣지 않고 따로 만드는 것

다음 다섯 가지는 매뉴얼 밖에 둡니다.

1. **1~2쪽 요약 카드**: 편성 한 바퀴 순서와 결과 읽는 법. 시즌 직전 복습용입니다. 작업 보조물은 교육받은 사람이 일하는 도중에 보는 자료이기 때문입니다([ScreenSteps](https://blog.screensteps.com/job-aids-vs-training-guides)).
2. **설명회 진행표**: 목표, 시간 배분, 3장 시연 순서, 자주 막히는 곳. 강사 안내서는 별도 문서로 두는 것이 관행입니다([Univ. of Debrecen](https://elearning.unideb.hu/mod/page/view.php?id=236292), 검색 요약만).
3. **KBO 책임자의 도입 메시지**: 둔다면 KBO의 목소리로 씁니다([Prosci](https://www.prosci.com/blog/understanding-why-some-communications-work-and-others-dont)).
4. **판마다의 바뀐 점 안내**: 짧은 공지로 냅니다([Timefold Changelog](https://docs.timefold.ai/timefold-platform/latest/changelog), [N-SIDE](https://knowledge.n-side.com/production-app/how-to-compare-scenarios-or-versions-of-a-scenario)).
5. **의견 창구 운영**: 운영 자체는 매뉴얼 밖에서 합니다. 매뉴얼 14장은 창구가 있다는 것만 알립니다.

## 결론

**조사로 바뀐 이해가 두 가지 있습니다.**

**첫째, 표준 구성은 따로 발명할 필요가 없습니다.** 스튜디오의 단계 순서 자체가 업계의 4단계 흐름(Fastbreak), 최적화 문서의 순서(Timefold), 문서 표준의 업무 중심 구성(26514·Diátaxis)과 이미 겹칩니다. 그래서 매뉴얼의 일은 순서를 새로 짜는 것이 아니라, **유형을 장 단위로 갈라 섞지 않는 것**입니다.

**둘째, 변화 관리 관점에서 매뉴얼이 가장 공들여야 할 곳은 "왜 바꾸나"가 아닙니다.** 다음 세 곳입니다.

1. 2장 "담당자가 정하는 일"
2. 6장 "결과를 믿기 전에 점검부터"
3. 7장 "비교해 고르고 확정한다"

알고리즘 회피 연구는 사람이 고칠 수 있고 고를 수 있다는 사실이 수용을 만든다고 말합니다. 우리 스튜디오의 「여기서 갈림」과 요구 사항 점검은 이번에 본 공개 자료 어디보다 그 근거를 화면으로 잘 보여 줍니다.

**앞으로의 위험은 첫 결과의 흠입니다.** 담당자가 처음 본 결과에서 흠을 찾으면 신뢰가 빨리 무너집니다. 그러므로 첫 판에서 미리 정직하게 써 둘 것은 기능 목록보다 다음 두 가지입니다.

- 2장의 "할 수 없는 것"
- 10장의 "반드시 지키는 규칙을 다 지킬 수 없을 때"

## 정할 것

1. **2025년 실제 일정과의 비교를 어디에 둘까요?**
   - 매뉴얼에는 넣지 않는 것을 권합니다. 독자가 그 일정을 만든 사람들이고, 지금 업무 방식을 언급하지 않는다는 제약과 부딪힐 수 있기 때문입니다.
   - 소개 자료 7장에 "같은 조건에서 나온 숫자"로 넣을지, 아예 뺄지 정해 주세요.
2. **KBO 책임자의 도입 메시지(서문)를 받을까요?** 받는다면 매뉴얼 맨 앞에 붙일지, 별도 한 장으로 둘지 정해 주세요.
3. **시즌 중 다시 짜기(8장)를 첫 판에서 어떻게 할까요?** 자리만 두고 "곧 추가"로 표시할지, 아예 빼고 기능이 나온 뒤 판을 올릴지 정해 주세요.
4. **용어 풀이(12장)와 색인을 둘까요?** 권하는 안은 용어 풀이는 1~2쪽으로 두고, 색인은 PDF 검색으로 대신하는 것입니다.
5. **요약 카드와 설명회 진행표를 매뉴얼과 함께 만들까요, 나중에 만들까요?**
6. **화면의 「엔진」을 「자동 편성」으로 맞출까요?** 화면의 상태 표시는 "자동 편성", 「운영 방침 설명하기」 창은 "엔진"이라고 씁니다. 매뉴얼은 "자동 편성"으로 쓸 계획이며, 화면 쪽은 글만 바꾸는 단순 수정입니다.
